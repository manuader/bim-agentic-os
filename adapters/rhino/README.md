# Rhino .3dm adapter (no Rhino)

`bim_rhino.py` converts a BIM-IR `Project` JSON (exactly the Core default serializer shape) to a `.3dm` file and back with [rhino3dm](https://pypi.org/project/rhino3dm/) 8.17.0 (MIT, McNeel's openNURBS bindings). Rhino is not installed or needed. The BIM-IR schema is unchanged.

Install into an isolated environment and run the regressions:

```sh
python3.12 -m venv .tools/rhino
.tools/rhino/bin/python -m pip install --only-binary=:all: -r requirements/rhino.txt
.tools/rhino/bin/python -I tests/rhino/run.py
```

CLI: `python bim_rhino.py export PROJECT_JSON OUTPUT_3DM` and `python bim_rhino.py import INPUT_3DM` (prints the Project JSON). Errors print `{"error","detail"}` on stderr and exit 1.

## Mapping

- Model units are Meters. Import also accepts Millimeters (divided by 1000); any other unit is refused (`rhino_units_unsupported`).
- Layer `BIM` holds `bim.schema` (`bim-agentic-os.rhino/1`), `bim.project.id` and `bim.project.revision` as user strings. Child layers `BIM::Levels`, `BIM::Walls`, `BIM::Spaces`, `BIM::Documentation` hold the elements of each kind.
- Each element is one object whose Rhino object Id equals the BIM-IR Id. User strings `bim.id`, `bim.kind`, `bim.order`, `bim.dependencies` (JSON array), `bim.provenance.source` and `bim.provenance.approval` carry the rest. The two provenance values are JSON-encoded strings, because Rhino deletes a user string set to empty text.
- Wall: a capped `Extrusion` whose path is the wall axis and whose profile is the thickness x height cross-section centred on it. Base elevation is the first level dependency (0 without one).
- Level: a `Point` at (0, 0, elevation). Space: a closed axis-aligned `PolylineCurve` rectangle at its level elevation. Plan/schedule/sheet have no geometry in BIM-IR; they are marker points at the origin that carry identity only.
- Door and window (P8-09): the layout `IntentCompiler` emits and the IFC adapter reads, kind `door`/`window`, geometry `[ax, ay, bx, by, sill, height]` (the opening's two ends on its host wall axis in the host direction, then sill above the level and height) and dependencies `[level, host wall]`. Each is one object on `BIM::Doors` or `BIM::Windows` (these layers are created only when the project has doors or windows, so files without openings keep the P8-02 layers), with the same identity user strings as every element. Its geometry is the opening volume: a capped `Extrusion` built like a wall, path from end to end on the host axis at level elevation + sill, profile the host thickness x the opening height. The host wall stays one uncut extrusion (rhino3dm has no booleans).

On import, geometry comes from the Rhino geometry, not from the user strings: wall axis from the extrusion path, height and thickness from the profile, space corner and size from the outline, level elevation from the point, opening ends from the box path, sill from the box base above its level (snapped to 1e-9 m) and height from the profile. So a window raised in Rhino comes back with its new sill. Height, thickness and space size are snapped to 1e-9 m to remove transform noise, so export, import and export again gives the same records. Element order comes from `bim.order`. Millimetre coordinates first drop under 1e-6 mm of noise, as Core's `LengthUnits.NormalizeMillimetres` does, then are divided by 1000.

## Refusals

Unreadable files (`rhino_read_failed`), models without the BIM root layer (`rhino_not_bim`), another schema marker, other units, objects without BIM user strings (`rhino_foreign_object`), copied objects whose Rhino Id differs from `bim.id` (`rhino_identity_mismatch`), objects on the wrong category layer, wrong geometry types, walls that are not a horizontal axis with a centred rectangular profile, and rotated or non-rectangular spaces. Exported and imported projects pass the Core rules again (kinds and arities, finite values, wall rule, unique ids, dependencies, cycles). Walls and spaces must still stand at their level's elevation, level points must stay on (0, 0, elevation) and documentation markers at the origin (`rhino_elevation_mismatch`, `rhino_position_mismatch`): BIM-IR has no field for those moves, so they are refused instead of dropped.

Export never replaces a file. It writes into `OUTPUT.pending`, created exclusively (an existing file or symlink there, for example left by a crash, is refused with `output_exists`), and publishes it with a hard link, which fails if `OUTPUT` appeared meanwhile. The command line reports every failure, including malformed JSON, numbers outside the double range, very deep nesting and lone surrogates (`bim_ir_invalid`), as one JSON line on stderr; anything unexpected is `internal_error`, never a traceback.

## Stricter than Core

Input that Core accepts but this adapter refuses: UUIDs that are not lowercase text, members other than exactly the Core ones, kinds the Core `GeometryCodec` cannot decode (Core's `Compiler.Validate` allows any kind), revisions outside 32 bits, strings with lone surrogates, spaces with zero or negative width or depth (`rhino_space_geometry`), doors and windows outside the IntentCompiler/IFC rule (`rhino_opening_host`: dependencies not exactly `[level, host wall]` with the host wall depending on exactly that level, so a host wall without a level cannot hold one; `rhino_opening_geometry`: not 6 values (the `[offset, width]` hosted layout carries no sill or height), ends more than 1e-7 m off the host axis, not in the host direction, past its ends, sill below 0, a door sill other than 0, height not positive, head above the host top), and lengths a .3dm round trip cannot carry (`rhino_precision`): wall axis, height, thickness or space size under 1e-6 m, or any coordinate beyond 1e5 m (openings: width or height under 1e-6 m, an end or the sill beyond 1e5 m). The nil UUID is accepted, as in Core. Openings that overlap one another are not refused (nothing is cut here).

Import refuses an opening box that no longer fits its host as above (moved off the axis, past the wall end, a door lifted off its level, a window head above the wall top: `rhino_opening_geometry`), a box not as deep as its host wall is thick (`rhino_opening_geometry`; BIM-IR has no opening depth), and a box that is not a horizontal-path extrusion (`rhino_opening_geometry`).

## Draft import from any .3dm (P8-06)

`rhino_draft.py INPUT_3DM [--project-id UUID] [--wall-height M] [--wall-thickness M] [--arc-segments N] [--metres-per-unit F]` reads any `.3dm` (not only files this adapter wrote) and prints one JSON draft on stdout: `draft_version` 1, `status` "proposal", `persisted` false, `source` (file, units, metres_per_unit, objects), `options`, `project` (the proposed elements as a Core-shaped BIM-IR Project, revision 0), `proposals`, `unmapped` and `summary`. Nothing is written; the draft is a proposal to review, like the CAD drafts (`adapters/cad`), and no BIM-IR schema is added. `draft(path, **options)`, `draft_model(file3dm, source_name, **options)` (in-memory model) and `dumps(result)` are the Python entry points.

- Layers: the nearest layer on the object's full path (leaf first) whose whole name, case-insensitive, is a kind name decides the kind: `Levels`/`Level`/`Niveles`/`Nivel`, `Walls`/`Wall`/`Muros`/`Muro`, `Spaces`/`Space`/`Rooms`/`Room`/`Espacios`/`Espacio`/`Locales`/`Local`, `Doors`/`Door`/`Puertas`/`Puerta`, `Windows`/`Window`/`Ventanas`/`Ventana`. So the writer's `BIM::Walls` maps, and `BIM::Walls::Exterior` inherits walls (note `layer-inherited`, confidence x 0.9). `Wallpaper` or `Space frame` do not match. Every other object is `layer_unmapped` (the writer's documentation markers too).
- Walls: a writer-style extrusion (horizontal path = axis, vertical rectangular section centred on it) maps exactly (0.95). A vertical extrusion of a rectangular plan outline (Rhino `ExtrudeCrv`) gives the axis along the long sides' midline, thickness = short side, height = extrusion length (0.85, `footprint-rectangle`); a square outline is `wall_footprint_ambiguous`. A line or polyline gives one centreline wall per segment with the assumed `wall_height` (2.7 m) and `wall_thickness` (0.2 m) (0.5, `centreline`, `height-assumed`, `thickness-assumed`). Arcs (an `ArcCurve`, or a NURBS curve of degree >= 2 that is a horizontal circular arc, checked on 33 samples: rhino3dm itself stores arcs and circles as rational NURBS) are `arc_not_approximated` unless `arc_segments` N >= 2 asks for N equal-angle chords (0.3, `arc-approximated`); other NURBS and poly curves are `curve_unsupported`.
- Spaces: a closed, horizontal, axis-aligned rectangle (repeated and collinear vertices dropped in one linear pass, any winding, every corner turning the same way so crossed outlines are refused) gives `[x, y, width, depth]` (0.9); a vertical extrusion of one gives the same (0.8, `height-dropped`). Open curves (`open_curve`), other polygons and circles (`space_not_rectangle`) and rotated rectangles (`space_not_axis_aligned`) are unmapped, because BIM-IR spaces are axis-aligned rectangles.
- Levels: a point on a level layer is a level at its z (0.9). An object that carries the writer's identity (`bim.id` = object id) keeps its `bim.dependencies`, each once in order (note `dependencies-declared`), when they agree with the geometry: every declared level at the element's base (or none at z = 0), otherwise all are dropped (`declared-dependencies-ignored`). Only proposed elements of a lower kind (level < wall < space, so walls keep their level and spaces their walls and level) are kept; when some are dropped the note is `declared-dependencies-filtered` instead, and when all are dropped the geometry decides as below. Without them, a wall or space depends on the level at its base elevation (smallest id when several, note `level-ambiguous`); at z = 0 without such a level it has none (BIM-IR convention); otherwise one level per elevation is synthesized (0.6, `level-synthesized`, no source object, id derived from the project id and elevation, re-derived if that id is taken). Spaces from plain geometry get no wall dependencies.
- Doors and windows (P8-09): a writer-style box (horizontal path, centred vertical rectangular section) maps with 0.9 (`opening-axis-extrusion`), a vertical extrusion of a plan rectangle with 0.8 (`footprint-rectangle`, axis along the long sides' midline; square: `opening_footprint_ambiguous`); anything else is `geometry_unsupported` or `opening_extrusion_unsupported`. Once every wall is proposed, each opening goes on a host wall that holds it: both ends at one signed offset from the wall axis within half the wall thickness (parallel), between its ends (1e-7 m), the box base not below the wall base and its top not above the wall top. Walls with more than one dependency cannot host. The writer's declared host (`bim.dependencies` `[level, host]`) wins when it holds the opening; otherwise the holding wall on its exact axis, then the smallest id (`host-inferred`, plus `declared-host-ignored` when a declared host did not hold it and `host-ambiguous` when several walls did); none is `opening_host_missing`. An opening off the axis is projected onto it (`projected-to-host-axis`, confidence x 0.9), ends are ordered in the host direction (`reversed-to-host`), and a box depth other than the host thickness is noted (`depth-differs-from-host`). Sill = box base - host base (snapped to 1e-9 m); a door whose sill is not 0 is `door_sill_not_zero`. Dependencies are `[host level, host]` (`dependencies-declared` when they equal the writer's); a host at z = 0 without a level gets the level at 0, synthesized if needed (`level-added-for-opening` on the wall), because BIM-IR openings depend on `[level, host wall]`. Proposals are ordered level, wall, door, window, space, and `summary` counts `doors` and `windows`. The writer's own openings draft back to exactly their ids, dependencies and `bim_rhino.py import` geometry bytes.
- Ids: the Rhino object id, except per-segment walls from curves, whose ids are derived from SHA-256 of the object id and segment index (key `objectid:segment`). The project id is the option, else the writer's `bim.project.id` on layer `BIM`, else derived from the file bytes. Provenance is `rhino:<file name>` / `draft-unapproved`. Ids proposed twice (objects sharing an id: `duplicate_object_id`; a derived id equal to another object's id: `duplicate_id`) are unmapped for every copy, whatever the file order. Objects inside block definitions are `block_definition_member`.
- Non-finite coordinates (NaN, infinity, or overflow in metres) and floating-point arithmetic errors unmap their object (or only that segment of a polyline) as `degenerate`, and a failed object keeps none of its proposals; other exceptions are bugs and propagate; so do curves with fewer than two points. Values the P8-02 writer could not carry (`rhino_precision`: beyond 1e5 m, under 1e-6 m) are unmapped (`out_of_range`, `degenerate`) instead of proposed, and the whole proposal passes the writer's validation and range check.
- Units: Millimeters, Centimeters, Decimeters, Meters (divided, with Core's mm noise rule), Kilometers, Inches, Feet (multiplied). Other units are refused (`rhino_units_unsupported`) unless `metres_per_unit` is given. Heights, thicknesses and space sizes are snapped to 1e-9 m as on import.
- Unmapped reasons: `layer_unmapped`, `geometry_unsupported`, `curve_unsupported`, `open_curve`, `curve_not_horizontal`, `degenerate`, `arc_not_approximated`, `space_not_rectangle`, `space_not_axis_aligned`, `space_extrusion_unsupported`, `wall_extrusion_unsupported`, `wall_footprint_ambiguous`, `out_of_range` (beyond 1e5 m), `too_many_vertices`, `opening_host_missing`, `door_sill_not_zero`, `opening_extrusion_unsupported`, `opening_footprint_ambiguous`, `duplicate_object_id`, `duplicate_id`, `block_definition_member`, and a final `unmapped_limit` entry when the report is capped. `part` is the segment index for per-segment entries, else null.
- Determinism: proposals are sorted by kind (level, wall, door, window, space) then id, unmapped entries by object id, part and reason, so the bytes do not depend on object order. Caps: `max_file_bytes` (256 MiB), `max_objects` (100000), `max_proposals` (100000, checked as proposals are made) refuse with `draft_limit`; `max_vertices` (10000) unmaps the object; `max_unmapped` (10000) caps the report, which keeps only the smallest entries in memory while counting all of them.
- Roundtrip: drafting a writer-made file gives the writer's level, wall and space ids and dependencies and the same geometry bytes as `bim_rhino.py import`; exporting a draft project and drafting it again gives the same project bytes when both files have the same name. The file name is in every `Provenance.Source`, so under different names only the provenance differs.

## Limits

- The Core geometry codec has no arc walls or room boundaries, so none are written. A wall with an extra value is refused, not guessed into an arc. Openings are written as separate volumes, the host wall is not cut; frames, panels, swing and the `[offset, width]` hosted layout are not carried, and kind `opening` (a bare void) is refused.
- `.3dm` bytes are not reproducible: rhino3dm writes timestamps and random layer ids. Stability is checked on the imported records and object ids.
- Imported values with more than 9 decimals in height, thickness or space size differ from the original by under 1e-9 m. Output JSON matches Core's for ASCII text; Core escapes non-ASCII and some ASCII characters (`é`, `+`), Python does not do it the same way.
- The draft does not explode poly curves, block references or meshes, read openings drawn as curves, holes in a wall profile or boolean-cut breps, or infer wall-to-space dependencies from plain geometry.
- Not exercised in Rhino itself; evidence is real rhino3dm read/write in CI on Linux only.
