# Module contracts — v0.1

The evaluation-only DTO and evidence boundary is specified in [evaluation.md](evaluation.md). It leaves the existing BIM-IR and RPC schemas unchanged.

## Deterministic core

`Project(Guid Id, int Revision, Element[] Elements)` is intended semantic state. `Element` carries stable logical UUID, kind, geometry in metres, prerequisite IDs and provenance. Current wall geometry is `[x1,y1,x2,y2,height,thickness]`; this compact representation is version-0 prototype data, not a full geometry schema.

`Compiler.Validate(Project) -> ValidationIssue[]` rejects invalid geometry/identity/dependencies. `Compiler.Diff(before, after) -> ExecutionPlan` requires matching project and revision, emits create/update/delete operations and transitive dirty IDs. `BeforeHash`/`AfterHash` bind the serialized intended snapshots; this version's hashes depend on array order and are not a canonical semantic hash.

`ProjectStore.Commit(desired, plan, key) -> Project` compares optimistic revision/hash and publishes revision+receipt atomically. It commits intended state only; it must not claim native execution. Reusing a key for another payload is a conflict. Snapshot schema migrations, power-loss testing and journal replay remain gaps.

## Runtime boundary

`RoomCompiler.Compile(projectId, revision, RoomIntent) -> Project` uses clear interior dimensions and fixed west/south exterior anchors. Roles derive stable UUIDs from room ID. `NativeBatchContract.Preflight(before, after, plan)` validates both snapshots and requires the exact recomputed diff. `NativeBatchRequest(DocumentIdentity, IdempotencyKey, Before, After, Plan)` is carried by `Request` with `Operation="batch"`, exact saved `DocumentPath`, empty `Metres` and optional `Batch` payload.

The batch currently supports levels/walls only and requires an isolated `BIM-Agentic-Test*` non-workshared document plus exact `ProjectInformation.UniqueId`. It persists mapping, intended revision and receipts inside native ExtensibleStorage transactions. It rejects native deletes (untracked cascades), spaces and document kinds. This is a guarded development slice, not production-project authoring or a validated Test A room.

No Autodesk object crosses into core or a background worker. Requests target an exact saved document path and execute in `ExternalEvent` context, serialized. Every mutation needs explicit units, transaction status and readback. Unsupported commands fail visibly; unsupported documentation blocks complete-delivery status. A batch must preflight the entire operation set before mutation and roll back on native failure. Durability must live with native identity, not only a transient RPC response.

## Validation and delivery

Independent QA consumes native readback, intended invariants and deliverable contract. Generator success, host compilation and accepted API calls are separate evidence levels. A delivery is not validated until all required native elements and affected documents are checked. Current Test A/B gates remain open until saved/reopened RVT evidence exists.

## Agent work contracts

Each task owns named files and public signatures; implementation and review use clean contexts. Workers commit only their worktree changes. Controller integrates reviewed commits and reruns the full available gate. Review findings, unresolved blockers and exact evidence are persisted in the plan ledger and feature tracker.

Native transport routing: each Revit process listens on bim-agentic-os-2025-PID. The fixture result binds pipeName to processId; callers must supply that explicit endpoint. The CLI rejects missing/global endpoints before I/O. Routing does not replace exact saved document path and ProjectInformation.UniqueId checks.


## Experimental fixture checkpoint

`Request(Operation="fixture.checkpoint", Batch=existingResizeBatch, Checkpoint=FixtureCheckpointRequest(ParkingPath, ExpectedRevision, ExpectedMapping))` verifies an existing receipt without applying a batch. Authorization requires the child-process opt-in config, matching bootstrap result PID/pipe/path/document identity, exactly one owned fixture document and a new direct-child parking path. `BatchReceiptGuard` validates the batch/hash/revision/exact mapping; `BatchExecutor.VerifyReceipt` reads ExtensibleStorage and native geometry without mutation.

The checkpoint saves the fixture, switches to newly owned parking, closes/reopens the fixture, closes parking and reloads native storage for comparison. A failure reports its stage and saved/closed/reopened flags; it does not promise rollback of file operations. A dispatched timeout has unknown completion and must not be automatically retried. Documentation remains unsupported. Target build and pure guard tests do not establish native save/reopen success; see the native evidence record for execution status.

Compiler.Validate now emits dependency_cycle for cyclic logical dependencies. Iterative prerequisite removal runs in O(V+E) without recursion; missing references and duplicate identities remain independently reported. Diff rejects a cyclic input snapshot and intended-state publication rejects cyclic commits. This is graph validation, not a complete dimensional or native BIM QA contract.

## Compiler-to-IFC adapter (narrow rectangle slice)

`adapters/ifc/Bim.Ifc.Compiler` owns an adapter request, separate from saved Core records. It carries exact default C# serialized before/after/plan strings, raw UTF-8 SHA256 bindings, room/operation identity, six physical logical-role UUIDs and the three unsupported documentation UUIDs. Export recomputes the exact Core diff and reconstructs the canonical RoomCompiler output; malformed, stale, cyclic, unsupported and tampered inputs are rejected. Python independently validates the packet and dependency closure before output mutation. Python JSON reserialization is not a Core hash oracle.

Export decodes the space and west wall through the Core `GeometryCodec` (ADR0008); a west element whose Kind is not `wall` (for example `beam`) now fails with `unsupported_ifc_rectangle` instead of the former `unsupported_ifc_noncanonical_room`.

Supported physical scope is one canonical rectangle, level/four walls/space, width-only corrections with fixed anchors/depth/height/provenance and200mm walls; minimum dimensions accommodate adapter-owned door/window fixture extras. Plan/schedule/sheet nodes remain in intended state and dirty closure but have no authored native documentation. Extras are explicitly not Core-authored elements. The deterministic join policy extends horizontal walls over corners and leaves vertical walls between inner faces, converting metre centreline geometry into millimetre IFC bodies.

The committed snapshot increments revision after applying a same-revision plan. Its hash must bind that committed revision, while the receipt separately binds the original plan payload. The next correction must validate against the committed snapshot; a first resize alone cannot establish this invariant. Retry requires a matching payload and consistent reopened persistent state/identity/geometry. Full A/B execution requires an actual correction; a low-level no-op must preserve file bytes and cannot fabricate a rollback observation. Staged failures must preserve the original persisted model; crash/power-loss durability remains outside this proof.

Core UUIDs are persisted in `BimCompiledIdentity`; IFC GlobalIds and STEP identities remain stable through corrections. Before/after physical readback is checked against intended boxes and independent world triangulation/schema validation. CLI `ifc-export before.json after.json plan.json room-guid operation-id` emits the adapter envelope. The evaluator uses the same export service for its default5→5.4m case; custom widths are tested separately without weakening its fixed master A/B oracle.

## glTF 2.0 export for Blender interchange (P8-04)

`adapters/gltf/Bim.Gltf` (BCL-only, references `core/Bim.Core`) converts a compiled BIM-IR `Project` into a `.glb` or a `.gltf` with an embedded buffer; [README](../../adapters/gltf/README.md). Input must pass `Compiler.Validate` and `GeometryCodec.Problem`; at most 10 000 elements; coordinates (including wall face corners) within ±1e4 m and lengths of at least 1 mm (`gltf_precision`); `WriteGlb` never overwrites (`output_exists`) and removes its own file on a failed write. One root node per project and one child node per element named `<kind> <id>` with extras `{bim_id, kind, type (always null), level}`; walls become centre-line boxes from their level elevation, spaces their interior rectangle at level elevation, levels empty nodes at their elevation, documentation empty nodes. Metres, BIM Z-up mapped to glTF Y-up as (x, y, z) → (x, z, −y), per-kind materials. Output bytes are deterministic across OS and culture (golden SHA-256 in `tests/gltf`). Export only: no import, no CLI command, no openings or slabs (not in BIM-IR), not run in Blender. Status: unit-tested.

## glTF export CLI verb and wall openings (P8-07)

`interfaces/cli` adds `export-gltf project.json output.glb|output.gltf` (positional, like the other verbs; `GltfExportCommand.cs`, one `case` line in `Program.cs`). The input goes through `BoundedInput` (8 MiB, regular file, no links; `input_*` codes); malformed JSON is `bim_ir_json_invalid`. The output path is bounded before the input is read: extension `.glb` or `.gltf` (case-insensitive, else `output_extension_unsupported`), an existing parent directory (`output_directory_not_found`) that is not itself a link and no link at the path, even dangling (`output_link_rejected`), no Windows `\\.\` or `\\?\` namespace (`output_not_regular_file`), empty or unparsable paths or any `:` after a drive designator (NTFS alternate data streams, refused on every OS) `output_path_invalid`, other create/write failures `output_io_error` (detail is the exception type name), and never an existing file or directory (`output_exists`, re-checked by the exclusive `GltfExporter.WriteNew` create). Success prints `{status:"succeeded", format, output, bytes, sha256, elements, openings}`; refusals print `{status:"failed", code}` (exporter refusals add `detail`), exit 1, and write nothing. The bytes equal `GltfExporter.ExportGlb` / UTF-8 (no BOM) `ExportGltf`, so reruns are byte-identical. `Bim.Gltf` now cuts openings: BIM-IR `door`/`window` elements as `IntentCompiler` emits them (`[ax,ay,bx,by,sill,height]`, dependencies `[level, host wall]`, no schema change) split their single host wall's box into solid boxes: openings are rectangles in the wall plane (along × height), the axis is split at every opening end and each stretch keeps its uncovered height bands bottom up (piers, sill walls, lintels, bands between a door and its transom or between stacked windows; 24 vertices and 12 triangles each, ends at `A + t·u`, touching faces coincide, so the mesh is not one closed manifold); the opening node is empty with extras `host`. Refusals: `gltf_opening_geometry` (other arity such as hosted `[offset, width]`, which carries no sill or height, or a non-positive width or height), `gltf_opening_host` (not exactly one wall dependency), `gltf_opening_outside_wall` (more than 1e-6 m off the axis, past its ends, negative sill or above the top), `gltf_opening_overlap` (overlap by more than 1e-6 m along the axis and in height), `gltf_precision` (a remaining part under 1 mm; gaps within 1e-6 m snap closed). Kind `opening` stays `geometry_kind_unsupported`. Projects without openings keep the P8-04 golden bytes; the opening fixture has its own `.glb`/`.gltf` goldens from an independent reimplementation, equal on Linux, Windows and macOS. The CLI link check covers the path and its immediate parent only. Status: unit-tested (`tests/gltf`, `tests/cli`); not opened in Blender.

## Isolated native Room A/B port

`fixture.room.ab` is a bounded fixture operation using the existing Request fields: exact DocumentPath, UniqueId=ProjectInformation.UniqueId, empty Metres and null Batch/Checkpoint. It runs through the serialized ExternalEvent only. It does not widen primitive batch support or change saved Core records.

The adapter persists its unchanged Core Project, logical/native map and original operation receipt in fixture-specific ExtensibleStorage. A retry compares both the original request hash and the independently hashed committed revision. Hosted door/windows, dimension and 3D view are explicit adapter fixture extras; this is not arbitrary BIM-IR authoring.

The native envelope binds protocol1, actual Revit build, exact execution source, real reopened observations, eight mandatory backend checks, measured metrics with scope and basename artifacts. The C# port validates opt-in configuration/result, document identity/path, live Revit PID and actual same-user pipe server PID. Only actual execution can produce runtime provenance; offline parser tests cannot. Missing prerequisites or a dispatched timeout never imply success. Timeout means unknown completion and prohibits automatic replay.

`total_ms` measures width correction through regenerated documentation, save-close-reopen, QA and persisted retry. `revit_execute_ms` covers the whole A/B fixture lifecycle. Unknown stages remain null with reasons. Read/write counters explicitly exclude prerequisite enumeration and helper placements. Native observations normalize only floating conversion noise within0.000001mm; actual room boundaries, dimension references/value and schedule cells are read independently.

Native capability selection uses actual `GetSchedulableFields()` entries matched uniquely by built-in parameter ID; no field-type assumption. Door-width readback records actual instance/type HasValue, storage type and internal values. A positive finite instance value takes precedence even when wrong; otherwise an actual positive finite type value is read. Missing both fails closed. The expected900mm is never a readback fallback. Partial error envelopes retain exact diagnostics under strict metadata checks and always remain blocked.

## Revit command protocol and catalogues v1 and v2 (ADR0009, C02, P9-01, P9-05)

`core/Bim.Core/RevitCommands*.cs` holds the vendor-free contract; the add-in executor (C03) consumes it. Request envelope `{protocol_version: 1, operation_id, document: {path, unique_id}, command, args}`: `operation_id` (1–128 of `[A-Za-z0-9._:-]`, alphanumeric first) is the idempotency key; `document.path` is the exact saved absolute path and `document.unique_id` the ProjectInformation UniqueId. `RevitCommandProtocol.Parse` rejects unknown or duplicate members and strings that are not valid UTF-16 (lone surrogates), validates `args` against the catalogue schema (a final `$` in a pattern means end of string, so a trailing newline is refused), then binds typed arguments: lengths in millimetres become Core `Length`, angles in degrees become `Angle`; non-finite, overflowing (`1e400`), beyond 1e8 mm, and negative or zero values where invalid are refused.

Response `{status, code, field, detail, created[], modified[], deleted[], readback, receipt, warnings[]}`: element lists hold stable UniqueIds; `receipt` (`operation_id`, `command`, `document_unique_id`, `request_sha256`, `replayed`) is required on success. The client reports a success only when the receipt's operation_id, command, document UniqueId and request_sha256 equal the request's; otherwise, and for any malformed reply, it reports `response_invalid` instead of the reply. A well-formed failure reply is passed through verbatim.

Hash contract for C03: `request_sha256` is the lowercase hex SHA-256 of the UTF-8 bytes of the `Command` member exactly as received on the pipe (the canonical envelope: members sorted ordinally, numbers as shortest round-trip doubles with -0 written as 0, default JSON escaping). The executor must hash that text as sent, not a re-serialization. The hash binds text, not meaning: an omitted defaulted field (`base_offset_mm`, `structural`) and the same field written with its default value give different hashes, so a retry must resend the same envelope.

Catalogue v1 (`RevitCommandCatalogue.V1`, one entry per command with name, read/write, args JSON Schema and a plain-English description): read-only `query.levels`, `query.wall_types`, `query.floor_types`, `query.family_symbols {category: door|window}`; writes `wall.create {level, type, base_offset_mm?, height_mm, structural?, curve}` where curve is `{kind:"line", start, end}`, `{kind:"arc", start, end, through}` or `{kind:"arc", center, radius_mm, start_angle_deg, end_angle_deg}` (counter-clockwise); `opening.place {category: door|window, symbol, host_wall_uid, position_along_mm, sill_mm?}` (`sill_mm` only for windows); `floor.create {level, type, boundary}` (3–1000 vertices, implicit closing edge); `room.create {level, point, name?, number?}`. The category vocabulary `door|window` is the same in both commands. 1.2 mm (Revit's short-curve tolerance) is the minimum for curves, edges, wall height, arc chord and arc sagitta. Arcs must not be collinear (a sagitta under 1.2 mm counts as collinear), need radius > 0 and at most 9 144 000 mm (Revit's 30000 ft limit, `RevitCommandGeometry.MaxRevitLengthMm`), a sweep strictly between 0 and 360 degrees, and centre ± radius within 1e8 mm. Wall height and the absolute base offset are capped at the same 9 144 000 mm (`length_invalid`). Floor outlines are taken relative to their first vertex. Edges that cross, touch or come within 1.2 mm of each other, or a vertex within 1.2 mm of a neighbouring edge, are refused as self-intersecting.

Catalogue v2 (`RevitCommandCatalogue.V2`, P9-01; same envelope, protocol_version 1, schema subset, unit rules, guards and receipts as v1; v1 is unchanged): read-only `query.roof_types`; writes `roof.create_footprint {level, type, boundary, slope_deg?, sloped_edges?, base_offset_mm?}` (closed non-self-intersecting outline, flat when `slope_deg` is omitted, otherwise one slope greater than 0 and at most 85 degrees on every edge, or only on the edges `sloped_edges` lists: distinct 0-based indices where edge i runs from vertex i to vertex i + 1 and the last edge closes back to vertex 0, so a gable on a rectangle lists its two long sides; `sloped_edges` needs `slope_deg` (`args_invalid`), an index out of range or repeated is `args_invalid` at `args.sloped_edges[i]`, and with a partial list the rise bound uses the largest vertex distance instead of half the minimum width; the executor matches each `NewFootPrintRoof` model curve to its requested edge by end points (1e-3 mm, either direction), never by mapping order, and the readback matches the sketch edges the same way and reports `start`, `end` and `boundary_edge` per sketch edge and `sloped_edges`, the boundary edges whose sketch edge defines slope as read from the roof), `stair.create {base_level, top_level, run: {start, end}, width_mm}` (one straight run between two distinct levels), `curtain_wall.create {level, type, base_offset_mm?, height_mm, curve, grid?: {vertical_spacing_mm?, horizontal_spacing_mm?}}` (a Curtain kind wall type, line or arc curve as `wall.create`, at most 500 extra grid lines per direction on this wall only) and `floor.create_opening {host_floor_uid, profile}` (closed non-self-intersecting profile through an existing floor). `RevitCommandCatalogue.All` is v1 then v2 (then any later entry); `Find`, the protocol, the permission policy and the MCP server all enumerate it.

Element queries (`RevitCommandCatalogue.Elements`, P1-02, core `RevitCommandsQuery.cs`; read-only, no transaction, no receipt, `read` permission on any document): `query.elements {category?, level?, parameters?, limit?}` needs a category, a level or both. `category` is a friendly name (`wall`, `door`, `window`, `floor`, `ceiling`, `roof`, `room`, `stair`, `railing`, `column`, `structural_column`, `structural_framing`, `structural_foundation`, `furniture`, `casework`, `plumbing_fixture`, `lighting_fixture`, `generic_model`, `curtain_panel`, `curtain_mullion`, `level`, `grid`; table `RevitElementQueryRules.Categories`) or a Revit BuiltInCategory name matching `^OST_[A-Za-z][A-Za-z0-9_]*$` (an unknown one is `reference_not_found` in the add-in); `level` is a level name or UniqueId and matches `Element.LevelId`, else the element's `FAMILY_LEVEL_PARAM`, `SCHEDULE_LEVEL_PARAM` or `INSTANCE_REFERENCE_LEVEL_PARAM`; `parameters` is 1–16 distinct names read on the element, then on its type (lowest parameter id when a name repeats; absent names are listed in `missing_parameters`), default `ALL_MODEL_MARK` and `ALL_MODEL_INSTANCE_COMMENTS`; `limit` is 1–5000, default 1000. Elements without a category and element types are skipped; without a category filter (level only) only model categories (`CategoryType.Model`) are kept, so views, sheets and annotations are not listed. The reply `{category, built_in_category, level, limit, matched, returned, truncated, truncated_reason, elements}` lists the lowest element ids first (`RevitElementQueryRules.Page`; `truncated` is the paging cut at the limit or the byte budget, `truncated_reason` `limit`, `bytes` or null; an element that vanishes between paging and reading lowers `returned` without setting `truncated`), each `{id, unique_id, category, built_in_category, level: {name, unique_id}|null, family, type, type_unique_id, parameters, missing_parameters}`. `query.inspect {unique_id}` returns `{element, parameter_count, returned, truncated, truncated_reason, parameters}` with every instance and type parameter that has a definition, ordered by name (ordinal), instance before type, then id, at most 2000. Each parameter is `{name, id, built_in, source: instance|type, storage_type: string|integer|double|element_id|none, spec, has_value, read_only, shared, value, unit, value_unique_id, display, value_truncated}`: doubles are routed by `RevitParameterUnits.ForSpec` on the spec id without its version suffix: lengths (`autodesk.spec.aec:length`) in `mm`, areas in `m2`, volumes in `m3`, angles in `deg`, other measurable specs in the document display unit (its unit type id) and anything else raw with `unit` null; element ids carry the referenced UniqueId; strings and display texts are cut at 1024 characters (`value_truncated`). Each reply is at most 4 MiB of UTF-8 (`RevitElementQueryRules.MaxReplyBytes`): rows or inspected parameters stop being added before the budget is exceeded, with `truncated_reason: bytes`. Unit-tested contract and reply JSON (tests/revit-commands/ElementQuery.cs); the collector `runtimes/revit-native/CommandsExecutorQuery.cs` is compiled only.

Structure commands (`RevitCommandCatalogue.Structure`, P9-02, core `RevitCommandsStructure.cs`; same envelope, protocol_version 1, schema subset, unit rules, copies-only guard and `operation_id` receipts as v1; earlier commands are unchanged): read-only `query.grids` (`{grids: [{name, unique_id, curved, start, end}]}`, sorted by name) and `query.structural_types {category: column|framing|foundation|wall_foundation}` (`{category, structural_types: [{family, type, reference, unique_id, active, placement_type}]}`; `reference` is `Family: Type`, or the type name for wall foundation types, whose `family` and `placement_type` are null; `placement_type` is the family's `FamilyPlacementType` name); writes `grid.create {line: {start, end}, name?}` (straight, 1.2 mm to 9144000 mm; the name has no leading or trailing space, none of the characters Revit refuses in names (`RevitViewRules.ForbiddenNameCharacters`), and no grid or multi-segment grid already uses it, ignoring case), `structural_column.create {type, point, base_level, top_level, base_offset_mm?, top_offset_mm?}` (vertical; distinct levels; the top, top level plus top offset, at least 1.2 mm above the base and at most 9144000 mm higher, else `levels_not_distinct` / `length_invalid`), `structural_beam.create {level, type, line: {start, end}}` (straight, in the reference level plane), `foundation.create_isolated {level, type, point}` (a `OneLevelBased` foundation family type, else `args_invalid` on `args.type`; under a column, give its point and base level) and `foundation.create_wall {host_wall_uid, type}` (a basic wall without a wall foundation, else `args_invalid` on `args.host_wall_uid`). Types resolve by UniqueId, type name or `Family: Type` (`reference_not_found` when absent or ambiguous); an inactive symbol is activated in the write and listed in `modified`. Each write is one transaction in a transaction group with an independent readback before commit and again after failure processing; any difference (1e-3 mm length tolerance) rolls the group back as `transaction_failed`. What is read back: grid: straight, plan end points in order, and the name when one was requested; column: type, `StructuralType` Column, not slanted, plan point, base and top level and both offset parameters (the column's absolute elevations are not read); beam: type, `StructuralType` Beam, reference level, plan end points in order and Start/End Level Offset both 0 (the curve's z is not read); isolated foundation: type, `StructuralType` Footing, level, plan point and the location point's elevation equal to the level's project elevation; wall foundation: type and host wall. Elements Revit adds alongside (joins, cut-backs, analytical elements) are not read back or listed. Readbacks: `{grid}`, `{structural_column}`, `{structural_beam}`, `{foundation}`, `{wall_foundation}`. Unit-tested contract, rules and readback (tests/revit-commands/CatalogueStructure.cs, runtimes/revit-native/CommandsStructure.cs); the executor `runtimes/revit-native/CommandsExecutorStructure.cs` is compiled only.

Documentation commands (`RevitCommandCatalogue.Documentation`, P4-02, core `RevitCommandsDocumentation.cs`; same envelope, protocol_version 1, schema subset, unit rules, copies-only guard and `operation_id` receipts as v1; earlier commands are unchanged): read-only `query.title_blocks` (`{title_blocks: [{family, type, reference, unique_id, active}]}`, sorted by family then type; `reference` is `Family: Type`); writes `dimension.create_linear {view_uid, first_uid, second_uid, line?: {start, end}, wall_face?: exterior|interior}` (a plan view (`FloorPlan`, `CeilingPlan`, `EngineeringPlan`, `AreaPlan`, not a template); two different references, each a straight grid (its line) or a straight wall (its one `HostObjectUtils.GetSideFaces` face on the `wall_face` side, default exterior, which must be planar and vertical; one `wall_face` applies to both references); the references must be parallel and at least 1.2 mm apart; a given line must be perpendicular to them (each end within 0.001 mm of a perpendicular line), else the line runs from the first reference's point straight across to the second; drawn at the view level's project elevation), `tag.create {view_uid, element_uid, head?, leader?, orientation?: horizontal|vertical}` (a plan view; a model element instance with a category, not a room, area or space; tag by category (`TagMode.TM_ADDBY_CATEGORY`) with the category's loaded tag; `head` defaults to the centre of the element's bounding box in the view; leader default false and only with `head`, else `args_invalid` on `args.leader`; orientation default horizontal), `schedule.create {category, fields, sort_by?, name?}` (`category` as in `query.elements`, which `ViewSchedule.IsValidCategoryForSchedule` must accept; 1–32 distinct schedulable field names matched ordinally on `SchedulableField.GetName`, `reference_not_found` at `args.fields[i]` when absent or ambiguous; Revit's default fields are removed first; `sort_by` is one of `fields`, sorted ascending; the name follows the view name rules and must be free among schedules and view templates, ignoring case), `sheet.create {number, name, title_block?}` (number and name follow the view name rules; the number must be free among sheets ignoring case, else `args_invalid`; `title_block` resolves by UniqueId, type name or `Family: Type`, an inactive symbol is activated and listed in `modified`; omitted, the sheet has no title block) and `sheet.place_view {sheet_uid, view_uid, center}` (a sheet that is not a placeholder; a view as a `Viewport` centred at `center` in sheet millimetres (within 100000 mm of the sheet origin), refused when it is a template, a sheet or browser view, already on a sheet (the sheet number is named; not checked for legends, which may appear on many sheets) or refused by `Viewport.CanAddViewToSheet`; a `ViewSchedule` as a `ScheduleSheetInstance` at that point, refused for title block revision schedules). Grids, walls, views, elements and sheets are given by UniqueId (`reference_not_found` when absent or of the wrong class). Each write is one transaction in a transaction group with an independent readback before commit and again after failure processing; any difference (1e-3 mm length tolerance, 1e-6 on unit directions) rolls the group back as `transaction_failed`. What is read back: dimension: owner view, exactly the two referenced elements, `Dimension.Value` equal to the reference distance in mm and the dimension line along the references' normal; tag: owner view, not orphaned, exactly the tagged element, leader, orientation and head point in plan; schedule: not a template, the definition's BuiltInCategory, the field names in order, the sort fields and the requested name; sheet: number, name and the type of each title block instance in the sheet (collected in the sheet view and owned by it) (none when none was requested); placement: viewport or schedule instance, sheet, view and centre (`Viewport.GetBoxCenter`, `ScheduleSheetInstance.Point`). Readbacks: `{dimension: {unique_id, view_unique_id, reference_unique_ids, value_mm, direction}}`, `{tag: {unique_id, view_unique_id, tagged_unique_ids, has_leader, orientation, head, orphaned}}`, `{schedule: {unique_id, name, built_in_category, fields, sort_fields}}`, `{sheet: {unique_id, number, name, title_block_type_unique_ids}}`, `{placement: {unique_id, kind: viewport|schedule, sheet_unique_id, view_unique_id, center}}`. Extrusion roof (`RevitCommandCatalogue.RoofExtrusion`, P9-07, core `RevitCommandsRoofExtrusion.cs`; same envelope, protocol_version 1, schema subset, unit rules, copies-only and link guards and `operation_id` receipts as v1; earlier commands are unchanged; an additive write, `destructiveHint: false`; listed after `document.save` and before `command.batch`, and a valid batch step): `roof.create_extrusion {level, type, plane: {start, end}, profile, extrusion_start_mm, extrusion_end_mm}` creates a barrel / curved sheet-metal roof (or any roof given by its section). `plane` is a plan line of `[x, y]` millimetres at least 1.2 mm long (`curve_too_short` at `args.plane`); the reference plane is the vertical plane through it. Frame: a profile point `[u, z]` is u mm along the line from `plane.start` and z mm above the reference level's project elevation (as `wall.set_profile`), each within 9144000 mm (`length_invalid` at `args.profile[i].start[k]` etc.); the roof is extruded along the line's left normal (its plan direction turned 90 degrees counter-clockwise) from `extrusion_start_mm` to `extrusion_end_mm` (each finite within 9144000, `length_invalid`; the end at least 1.2 mm greater than the start, else `length_invalid` at `args.extrusion_end_mm`). `profile` is 1 to 100 segments (`args_invalid` at `args.profile`), each `{kind: line, start, end}`, `{kind: arc, start, end, through}` or `{kind: arc, center, radius_mm, start_angle_deg, end_angle_deg}` (counter-clockwise with u right and z up; 0 degrees = +u), with the curved wall arc rules at `args.profile[i]` (`curve_too_short`, `arc_collinear`, `arc_radius_invalid`, `arc_sweep_invalid`). Profile rules, all before the pipe: connected in order (segment i must start within 0.5 mm of segment i-1's end, and is then snapped onto it; else `args_invalid` at `args.profile[i]`), open (the last end at least 1.2 mm from the first start; else `args_invalid` at `args.profile`), not self-intersecting (`args_invalid` at `args.profile[j]`, j the later segment: non-neighbours must not touch or come within 1.2 mm, by exact line/line, line/circle and circle/circle intersections plus the least distance over end points and the points where the connecting line is normal to both curves; neighbours may meet only at their shared end: no overlap or second crossing farther than 1.2 mm from it, neither far end within 1.2 mm of the other segment). Planarity holds by construction (two coordinates in the plane) and is read back. Example (6000 x 10000 cabin, 300 mm overhangs, eaves 2700, crown 3800): `plane [0,0] -> [6000,0]`, `profile [{kind: arc, start: [-300,2700], end: [6300,2700], through: [3000,3800]}]`, extrusion -300 to 10300 (centre (3000, -1700), radius 5500). Executor (`runtimes/revit-native/CommandsExecutorRoofExtrusion.cs`, rules in `CommandsRoofExtrusion.cs`): level and roof type by name or UniqueId (`reference_not_found`); in the one write transaction `Document.Create.NewReferencePlane(start, end, BasisZ, view)` at the level's elevation (view: a non-template plan of the reference level, else the active view; none is `transaction_failed`), then `NewExtrusionRoof(profile, plane, level, type, start, end)` with `Line.CreateBound` / `Arc.Create(start, end, mid)` curves in that plane; when the new plane's normal points opposite the left normal the extents are mirrored (`-end`, `-start`). Readback before commit and after failure processing, from the roof itself: reference level (`ROOF_CONSTRAINT_LEVEL_PARAM`, else `LevelId`) and type, the reference plane still exists, the `EXTRUSION_START_PARAM`/`EXTRUSION_END_PARAM` instance parameters (the 2025 API has no `ExtrusionRoof` properties for them) mapped back equal the request within 1 mm, every `GetProfile()` curve's sketch plane is parallel to the requested plane and its ends and midpoint lie within 1 mm of it, the curves equal the requested segments one for one (same kind, ends in either direction and midpoint within 1 mm; an arc Revit split reads back as a mismatch), and the bounding box spans at least the extents along the left normal within 25 mm (catches an extrusion to the wrong side); a difference rolls the group back as `transaction_failed`. `created` lists the roof and the reference plane. Readback: `{roof_extrusion: {unique_id, level_unique_id, type_unique_id, reference_plane_unique_id, plane_start_mm, plane_end_mm, extrusion_start_mm, extrusion_end_mm, profile_mm: [{kind, start, end, mid?}], bounding_box_mm: {min, max} | null}}`. Not offered: a reference plane given by UniqueId, non-vertical planes, eave cuts, closed profiles, setting the roof's level offset (z already places the profile). Unit-tested contract, profile rules, frame and readback (tests/revit-commands/CatalogueRoofExtrusion.cs, runtimes/revit-native/CommandsRoofExtrusion.cs); the executor is compiled only. Unverified in Revit: that the extents are measured along the reference plane's normal and read through those parameters, which view `NewReferencePlane` needs for a vertical plane, that Revit keeps the profile curves unsplit, and where the type's thickness sits relative to the profile line.

Client codes: `envelope_invalid`, `protocol_version_unsupported`, `operation_id_invalid`, `document_path_invalid`, `document_identity_invalid`, `command_unknown`, `args_invalid` (schema; `field` names the JSON path), `length_invalid`, `angle_invalid`, `curve_too_short`, `arc_collinear`, `arc_radius_invalid`, `arc_sweep_invalid`, `boundary_too_few_points`, `boundary_edge_too_short`, `boundary_zero_area`, `boundary_self_intersecting`, `document_not_enabled`, `document_link_refused`, `allowlist_invalid`, `explicit_process_pipe_required`, `request_too_large`, `pipe_connect_timeout`, `pipe_io_error`, `no_response`, `response_invalid`. Reserved for the executor: `operation_id_conflict`, `document_conflict`, `reference_not_found`, `transaction_failed`.

Copies-only guard: `RevitCopiesGuard.Check(writes, documentPath, policy)` is a pure function. Read-only commands pass on any well-formed absolute path; write commands pass only when the path equals or lies (by whole segments) under a `RevitCommandPolicy.EnabledRoots` entry, else `document_not_enabled`. Paths with `.`/`..` segments, device namespaces, alternate data streams or control characters are `document_path_invalid`. Drive and UNC paths compare case-insensitively, `/` paths exactly. Enabled roots are the repository's `.bim/native-runs` plus the lines of the owner file `.bim/revit-enabled-roots.txt` (git-ignored; the owner edits it by hand: one absolute path per line, `#` comments, at most 256 entries and 64 KiB). Both are found from the CLI or MCP binary location; neither a CLI argument nor an MCP tool call can add a root. A drive root, `/`, or a UNC path without server, share and one directory is too broad; such an entry, a malformed one, or an owner file that is a link, oversized or unreadable is `allowlist_invalid`, and the whole file is refused (MCP then answers writes with `allowlist_invalid` until the file is fixed; it re-reads the file when it changes, see Policy reload). The owner's "enable real project" list from OWNER.md is recorded as lines of that file.

Link guard: for write commands, after the text check and before the pipe, `RevitLinkGuard.Check` probes the matched root and every component below it down to the document. A component with a link target (symlink or junction) is refused; a reparse point without one (OneDrive placeholder) is allowed, as in CloudGuard. On Windows a document with more than one hard link (GetFileInformationByHandle) is also refused. Either refusal is `document_link_refused`. The probe is injectable (`RevitFileSystemProbe`). Components above the root are not checked. The check runs on the client machine at request time; the executor must repeat it on the document it opened, because any same-user process can write to the pipe.

Transport: `revit-command envelope.json process-pipe-name` checks the pipe name (`bim-agentic-os-2025-<pid>`) before any I/O, like `native`. An unreadable envelope file is `envelope_invalid`, reported in the response shape. The verb then parses, guards and writes one line in the existing `Request` shape, with `Operation="revit.command"`, `DocumentPath`, `UniqueId` = document UniqueId and empty `Metres`, plus `Command` = the canonical envelope (65536-character cap). It then verifies the reply as above and exits 1 unless the request succeeded. The MCP server generates one `revit_<command>` tool per catalogue entry. Each tool takes `{pipe_name, operation_id, document, args}`; `document` bounds `path` to 1024 characters and states the UniqueId pattern, and `args` is exactly the catalogue schema. Each tool runs the same `RevitCommandService.Run` and returns text byte-equal to the CLI's stdout. The add-in dispatches `revit.command` to the C03 executor (below) before any transaction starts; it no longer answers `unsupported_capability`. Evidence level: unit-tested (`tests/revit-commands`, fake in-process pipe server, real symlinks on Linux); nothing here has run in Revit.

MCP exposure (P9-05): `tools/list` is the four core tools then one `revit_<command>` tool per `RevitCommandCatalogue.All` entry, in catalogue order, generated when the server is built; no tool name or count is hardcoded, so a new catalogue entry is exposed without editing `interfaces/mcp`. Construction fails closed (`InvalidOperationException`) when two tool names collide (for example `a.b_c` and `a_b.c` both become `revit_a_b_c`), when a name does not match `^[a-zA-Z0-9_-]{1,64}$`, or when `PermissionPolicy.RequiredLevel` cannot classify an entry. Each Revit tool lists `inputSchema.properties.args` equal to the entry's `ArgsSchemaJson` and a description that starts with the entry's description. `_meta` holds `"bim-agentic-os/permission_level"`: the P10-03 level that `PermissionPolicy.RequiredLevel` gives the command on a test copy (`read` for queries, `write-copies` for writes; a write to any other document is `write-real-project` under that policy). `annotations` holds `readOnlyHint` (true only for reads) and, for writes, `destructiveHint: false` (commands only add elements) and `idempotentHint: true` (a retry with the same `operation_id` replays). Tool `annotations` and `_meta` are not part of the advertised 2024-11-05 protocol: they are best-effort hints that a client may ignore, and no decision depends on them. Enforcement stays in `RevitCommandService.Run` (copies-only guard, then link guard) for every catalogue version. The MCP server currently allows a write on any document under the repository `.bim/native-runs` or under any directory root listed in `.bim/revit-enabled-roots.txt`. It does not apply the P10-03 exact per-document enablement or per-actor grants, and it writes no audit log. A v2 write outside those roots is `document_not_enabled` before any pipe I/O; a v2 query is forwarded on any document, and each forwarded envelope carries the entry's `command`. Evidence level: unit-tested (`tests/mcp`, `tests/audit`, `tests/revit-commands`); not verified in Revit.

## Owner project mode (chat-open-project)

`scripts/owner-open-project.ps1 -Path <absolute .rvt>` opens an owner's existing project, uncopied, in a NEW child Revit with the command pipe; `-Stop` only removes a leftover staged manifest and reports whether the child is alive (it never closes or kills Revit). Admission is one Core decision, `OwnerProjectGuard.Check(path, policy, probe)` (`core/Bim.Core/RevitOwnerProject.cs`): an absolute normalized path (`document_path_invalid`), a `.rvt` (`project_not_rvt`) that is not a Revit backup `name.NNNN.rvt` (`project_backup_file`), under an enabled root of `RevitCommandPolicy` (the repository `.bim/native-runs` plus `.bim/revit-enabled-roots.txt`, else `document_not_enabled`), no link from that root down (`document_link_refused`) and an existing file (`project_missing`). ## Plan to catalogue commands (P3-02)

`PlanToCommands.Translate(ExecutionPlan, RevitBindings)` (or `Translate(Project, …)` for an all-create plan of a compiled layout intent) returns a `RevitCommandPlan`: `preconditions`, ordered `steps` and `unsupported`. It only consumes the catalogue: each step's args are built in millimetres and parsed by `RevitCommandProtocol.Parse` with the target document, so every emitted command already passed the catalogue schema, unit and geometry validators; `args` is stored canonical. Order: one read-only `query.levels` (when any wall or room is emitted), then `wall.create` (straight axis line, `height_mm`, bound level and wall type; defaulted fields omitted), then `opening.place` (centre distance from the host wall start, `sill_mm` for windows only), then `room.create` (interior centre point, no name or number); within a phase steps are sorted by element id, so plan operation order never changes the output. `depends_on` names earlier steps only: walls and rooms the level check, an opening its host wall, a room also its bounding walls. A host wall's UniqueId is unknown until it runs, so `host_wall_uid` holds `PlanToCommands.PlaceholderUniqueId` and `inputs` says `{field: "args.host_wall_uid", from_operation: <wall step>, select: "created[0]"}`; `PlanToCommands.Envelope(plan, step, created)` fills inputs from created UniqueIds and re-parses; it refuses an input whose field is not one `args.<member>` (`input_field_unsupported`), whose select is not `created[0]` (`input_select_unsupported`), whose step is not in `depends_on` (`input_not_dependency`) or that is missing (`input_unresolved`). Opening width and height are listed in `unmapped`: `opening.place` takes the size from the family type.

`RevitBindings` supplies what BIM-IR does not carry: the target document, an existing Revit level (name or UniqueId) per BIM-IR level id, wall types by thickness (duplicates refused), and one door and one window family type. `RevitBindings.FromIntent` binds intent level and wall type names; a thickness shared by differently named wall types stays unbound. Catalogue v1 cannot create levels, so a bound level create becomes a precondition (with `elevation_mm`) that the level already exists; levels referenced but not in the plan are preconditions with `action` null. Each precondition carries `check_operation`, the `query.levels` step id (null when no step is emitted). `PlanToCommands.CheckPreconditions(plan, readback)` checks them against that step's readback `{"levels": [{name, unique_id, elevation_mm, …}]}`: a UniqueId reference matches `unique_id` ignoring case, any other reference matches `name` exactly (as the executor resolves it); no match is `level_missing`, several are `level_ambiguous`, and a precondition with an elevation more than `PlanToCommands.ElevationToleranceMm` (0.001 mm) from `elevation_mm` is `level_elevation_mismatch`. A malformed readback is `response_invalid`.

Nothing is dropped: every plan operation is exactly one step, one precondition or one `unsupported` entry `{element_id, element_kind, action, code, detail}`. Codes: `action_unsupported` (update/delete; v1 has no such commands), `kind_unsupported`, `geometry_invalid` (including a door with a sill, a zero-width opening, or an opening centre more than 1e-6 m off its host axis), `level_unbound`, `wall_type_unbound`, `symbol_unbound`, `host_unresolved` (host wall not created by this plan), `dependency_unsupported` (level, host or bounding wall unsupported), `command_invalid` (catalogue refusal; detail `<code>@<field>: <detail>`). A room's own `command_invalid` is reported before a missing bounding wall.

Operation ids: `"op." +` the first 16 bytes, lowercase hex, of SHA-256 over the UTF-8 text `plan-to-commands/2\n<projectId:D>\n<expectedRevision>\n<afterHash>\n<elementId:D or empty>\n<command>\n<document unique_id>\n<document path>\n<canonical args>\n<input operation ids joined by ",">` (`PlanToCommands.OperationId`). The canonical args are the binding-derived args (level, wall type, symbol, lengths) without `host_wall_uid` while it holds the placeholder; the host enters through its step id instead. So a changed binding, document or host wall gives a new id rather than an `operation_id_conflict` on retry. The same plan and bindings give the same ids, so a retry replays receipts; a different plan, revision, command, binding or document gives different ids. `ToJson()` writes members in a fixed order (`bridge_version, catalogue_version, project_id, expected_revision, after_hash, document, preconditions, steps, unsupported`), so the same plan and bindings give byte-identical JSON. Evidence level: unit-tested (`tests/plan-to-commands`); nothing here has run in Revit.

## Plan runner (P3-03)

`PlanRunner.Run(RevitCommandPlan, IRevitCommandTransport)` executes a translated plan one step at a time. The transport is injected: `string? Send(string envelopeJson)` takes a canonical protocol envelope and returns the executor's `RevitCommandResponse` JSON (null: no reply); `RevitCommandService.Run(pipe, envelope, policy, PipeTransport).Line` has that shape. A plan without steps (a levels-only intent, or every element unsupported, so `check_operation` is null) completes with nothing sent. Otherwise, when the plan has preconditions it first sends their `query.levels` step (`levels_check_missing` if the plan lacks it; a repeated operation id is `plan_duplicate_operation`) and checks the readback with `PlanToCommands.CheckPreconditions`; any issue is `precondition_failed` and nothing else is sent. Each other step is built with `PlanToCommands.Envelope`, filling `inputs` from earlier steps' `created[0]`. A reply counts only if `RevitCommandResponse.Parse` accepts it, it succeeded, and its receipt repeats this request's operation_id, command, document UniqueId and request SHA-256 (as `RevitCommandService` checks). The first failure stops the run: an error reply keeps the executor's code, field and detail; a malformed reply or foreign receipt is `response_invalid` (`field: "receipt"` for the receipt, `field: "code"` for a failed reply with code `ok`); no reply is `no_response`; a transport `TimeoutException` is `pipe_connect_timeout` and any other transport exception `pipe_io_error`, with only the exception type name as detail. Malformed replies and readbacks get fixed details (`PlanRunner.MalformedReplyDetail`, `MalformedReadbackDetail`), never a parser message; a success with an empty `created` while a later step takes its `created[0]` is `created_missing`.

The report (`RevitPlanRunReport`, `ToJson()`/`Parse`) is `{runner_version: 1, plan_sha256, status: completed|failed|precondition_failed, levels_check: {operation_id, issues: [{element_id, level, code, detail}]} | null, completed: [{operation_id, command, element_id, created, replayed, warnings}], failed: {operation_id, command, element_id, code, field, detail} | null, pending: [operation_id]}` with members in that order, so the same plan and replies give byte-identical JSON. `plan_sha256` is the SHA-256 of the plan's `ToJson()`. `completed` is a prefix of the plan's steps (the level check excluded) and `pending` the rest; a failed write step is `pending[0]`. `levels_check` is null when the plan has no level check or the check itself failed, and otherwise names the plan's check, with issues exactly when the status is `precondition_failed`. `Parse` reads any string `ToJson()` writes (empty included) and refuses missing, extra, duplicate or mistyped members (`report_invalid`). `PlanRunner.Resume(plan, report, transport)` refuses a report of another plan (`report_plan_mismatch`) or one that does not fit it (`report_invalid`: `runner_version` not 1, steps out of order or missing, a completed or failed step whose command or element differs from its plan step, a created entry that is not a UniqueId, a failed step that is neither `pending[0]` nor the level check, a `levels_check` inconsistent with the rules above, a contradictory status, a needed `created[0]` missing), re-sends the read-only level check (the document may have changed), then only the pending steps; completed steps are never resent and their `created[0]` feed pending inputs. A pending step that had in fact run (reply lost) is resent with the same operation_id, so the executor replays its receipt (`replayed: true`) and writes nothing; it counts as done. The same replay means `created_missing` does not clear on resume: the receipt answers with the same empty `created`, the step fails again and nothing new is written. A completed report resumes to itself without sending anything. The runner does not refuse a plan that has `unsupported` entries; it runs the steps that exist. Evidence level: unit-tested with a fake transport (`tests/plan-to-commands/PlanRunnerTests.cs`); nothing here has run in Revit.

## Revit command executor (C03)

`runtimes/revit-native/CommandsExecutor.cs` runs on the ExternalEvent thread. The decisions that need no Revit object (`CommandsContract.cs`, `CommandsReadback.cs`, `CommandsGate.cs`) are unit-tested in `tests/integration/RevitCommandGuard.Tests`; the Revit half is compiled in CI only and becomes verified-in-revit with C04.

- Exposure: without `BIM_AGENTIC_TEST_CONFIG` the add-in creates no ExternalEvent and opens no pipe, so a production Revit that loads the manifest exposes nothing. With it, both start only after `FixtureBootstrap` validated the config and opened the fixture, just before the result file is published; a bootstrap that fails afterwards withdraws them.
- Binding: `request_sha256` is the SHA-256 of `Request.Command` exactly as received (`JsonElement.GetRawText`); the envelope is parsed again with the Core protocol, and the outer `DocumentPath`/`UniqueId` must repeat it (`envelope_invalid`).
- Admission: the active document's ProjectInformation UniqueId and `Document.PathName` must equal the envelope (`document_conflict`). Writes then repeat `RevitCopiesGuard` and `RevitLinkGuard` on `Document.PathName` as opened, and refuse read-only, family and workshared documents (`document_not_enabled`) or an open transaction (`transaction_failed`). The legacy primitive operations (`level.create`, `wall.create`, `wall.axis.update`, `element.delete`, `batch`, and any unknown one; only `inspect` reads) pass the same write guard before they run.
- Allowlist location: the add-in finds the repository by walking up from its own assembly folder to `global.json` and uses that repository's `.bim/native-runs` plus `.bim/revit-enabled-roots.txt`. Runs (the staged add-in and the fixture) must therefore live under the repository, normally `.bim/native-runs/<run>`; an add-in staged elsewhere enables no write at all.
- References: a value shaped like a UniqueId matches only by UniqueId; otherwise it must equal exactly one name (or `Family: Type` for family symbols). None or several is `reference_not_found`. Stacked wall types are refused by `wall.create`; curtain walls and hosts whose `WALL_KEY_REF_PARAM` is not Wall Centerline are refused as opening hosts (not projected); foundation slab types are not floor types. `query.wall_types` reports `width_mm` only for basic walls.
- Idempotency: receipts live in one DataStorage with its own ExtensibleStorage schema (`f1ab754d-5370-4412-9d79-7066e4627326`), keyed by operation_id. Only writes read or record them; queries never touch the store. Same operation_id and hash returns the stored response with `replayed: true` and writes nothing: the readback in a replay is the stored one from the first run, not a fresh read. Same operation_id with another hash is `operation_id_conflict`. The store holds at most 2000 receipts and 4 MB; a new write beyond that is `transaction_failed` "receipt store full" (replays still work). An unreadable store fails closed.
- Writes: one TransactionGroup per command. Apply, regenerate, read back and compare (`CommandReadback`), commit, read back again after Revit's failure processing, persist the receipt, assimilate. Any failure rolls the whole group back and answers `transaction_failed` with Revit's message or the readback mismatch. Revit warnings are deleted in the failures preprocessor (so no dialog blocks the ExternalEvent) and reported in `warnings`; any Revit error rolls back.
- Coordinates: plan XY and elevations are Revit internal coordinates (the internal origin), converted with `UnitUtils` to millimetres; they are not Project Base Point or Survey Point coordinates.
- Durability: a success means the change and its receipt are committed in the open document in memory. The executor does not save; nothing is on disk until the document is saved, and closing without saving loses both the elements and the receipt.

## Offline classification mapping (P10-05)

`core/Bim.Core/Classification.cs` (BCL only) maps BIM-IR elements to classification codes from a checked-in, versioned dictionary; nothing is fetched at run time (bSDD-style, offline). Data and licence notes: [Classification README](../../core/Bim.Core/Classification/README.md).
- Dictionary format `bim.classification-dictionary/1` (new, additive): required `format`, `id` (`^[a-z0-9][a-z0-9.-]{0,63}$`), `version` (semver x.y.z), `name`, `publisher`, `edition`, `retrieved` (calendar date YYYY-MM-DD), `source_url` (absolute https), `licence`, `code_pattern` (anchored regex, 100 ms budget), `rules` [{`kind`, `code`, `title`, `location` (https)}]; optional `edition_date` (IFC4 IfcDate YYYY-MM-DD checked with `DateOnly.TryParseExact`; absent or null when the publisher gives only a month, which then stays in `edition`) and `unmapped` [{`kind`, `note`}] for kinds deliberately left unclassified. Labels and identifiers are at most 255 characters (IfcLabel/IfcIdentifier), URLs 512, notes 512, licence 2048.
- `ClassificationDictionaryParser.Parse`/`LoadFile`/`LoadBuiltIn(id)` are strict: at most 65 536 bytes (file and resource reads are bounded), strict UTF-8 with one optional BOM, no comments or trailing commas, JSON depth at most 8, lone surrogate escapes refused (`classification_invalid_json`), duplicate JSON keys, unknown members, a missing or non-string member, a code outside the base pattern `^[A-Za-z0-9][A-Za-z0-9 ._-]{0,63}$` or the dictionary's `code_pattern` (compiled with `RegexOptions.NonBacktracking`, so backreferences and lookarounds are refused), a kind given twice (rules and exclusions together) and more than 256 entries are all refused with a `ClassificationException` whose `Code` is a `classification_*` constant and whose `Path` is a JSON path. File-system failures, including an empty or malformed path, are `classification_read_failed`. Built-in dictionaries are the embedded resources `Bim.Core.Classification.<id>.json` (`BuiltInIds`); an unknown or malformed id is `classification_unknown_dictionary`.
- Rules are keyed by element kind only: BIM-IR `Element` has no type, predefined type or internal/external flag, so door vs window is the only distinction available.
- `Classification.Map(dictionary, Project | Element | elements)` returns `ClassificationResult{DictionaryId, DictionaryVersion, Mapped, Unmapped}`, both lists ordered by element id (ordinal over the lowercase `D` Guid form), independent of input order. ## Mirror drift against the Core store (P2-04)

`core/Bim.Core/MirrorDrift.cs` compares a `query.snapshot` (`MirrorSnapshot`, or its JSON reply via `MirrorDrift.ParseSnapshot`) with the Core store's committed BIM-IR for the same document (`MirrorCommittedModel`: document UniqueId, the persisted `Project`, and the logical map BIM-IR id -> Revit UniqueId the add-in keeps in ExtensibleStorage). Pure, Revit-free, unit-tested in `tests/mirror-journal` (fixtures in `tests/mirror-journal/fixtures/drift`); not wired to a CLI or Revit command yet.

- Identity: the snapshot and the model must name the same ProjectInformation UniqueId (ignoring case), else `drift_document_mismatch`; blank is `drift_document_required`. Elements match by Revit UniqueId (ignoring case); two committed ids on one UniqueId is `drift_map_invalid`. A snapshot reply that maps one UniqueId twice (ignoring case) is `drift_snapshot_invalid`.
- Map shape: `MirrorCommittedModel.Parse` accepts `{"document_unique_id","project","map"}` and `MirrorCommittedModel.FromNativeState` the add-in's persisted State payload (`{"Project","Map","Receipts"}`). Map keys that are Guids are BIM-IR ids. Other keys (the native Room fixture's `fixture:door`, `fixture:window-east`, `fixture:window-north`, family symbols `door-symbol` / `window-symbol`) are the add-in's own elements: their UniqueIds are claimed (never `extra`), listed under `not_comparable` with reason `map_key_not_bim_ir`, `map_key` and the snapshot kind (or ""), and counted in `summary.ignored_map_keys`. Two map entries naming one UniqueId are `drift_map_invalid`; a non-string value is `drift_model_invalid`.
- Comparable kinds: only what `query.snapshot` exports (level, wall, door, window, space). Other committed kinds (plan, schedule, sheet, ...) are listed under `not_comparable` (reason `kind_not_exported`), claim their UniqueId (so the element is never `extra`) and are never drift: a pristine `RoomCompiler` model has no drift.
- Findings: `missing` (committed, not in the snapshot; a committed element with no map entry is missing with evidence `map:missing`), `extra` (mapped in the snapshot, not committed), `changed` (field-level: geometry by named BIM-IR field within `length_tolerance_mm`, default 1 mm; axis direction of walls, doors and windows within `angle_tolerance_deg`, default 0.1, compared across the +-180 wrap; kind exact). Dependencies are compared as UniqueId sets by role, never by order: `level` (dependencies of kind level; skipped for a Core space that lists no level, the `RoomCompiler` form) and `host` (doors, windows), `bounding_walls` (spaces) or `dependencies` (anything else). Matching pairs without differences count as `unchanged`. A `RoomCompiler` space lists only its bounding walls, so its level is never checked: a room moved to another level in Revit shows only through its walls' `level` fields.
- Scope (`options.scope`): `map_only` (default) counts an unowned snapshot element (no committed element or map entry claims its UniqueId) as `extra` only when journal or receipt evidence names it; otherwise it is listed under `out_of_scope` (template levels such as Level 2, content that predates Core) and never counted. `document` counts every unowned mapped element as `extra`. Other values are `drift_options_invalid`.
- Classification: `external_edit` when a journal entry with origin `external` (after `journal_after_sequence`) names the element; `addin_pending` when only add-in journal entries or command receipts on or after Core's committed revision (`MirrorAddInReceipt.CoreRevision >= Project.Revision`) name it; `unknown` without evidence. External evidence outranks add-in evidence; all evidence is listed (`journal:<seq>:<origin>`, `receipt:<operation_id>`). For `missing` elements only, a journal deletion whose element id equals the hex suffix of the UniqueId (Revit's `<episode guid>-<element id>` convention, not an API guarantee) is weaker evidence labelled `journal:<seq>:<origin>:deleted_id_match`. Origins other than `external` / `add-in` are refused (`drift_journal_invalid`). Evidence for another document is ignored and counted.
- Add-in evidence: the production recorder skips the add-in's own transactions (`MirrorJournal` default `recordAddIn: false`), so in practice `addin_pending` comes from receipts. The add-in's stored receipts (`CommandsContract.cs`) carry no Core revision; the caller that dispatched the command (plan runner / CLI) builds `MirrorAddInReceipt` from the receipt's operation id, the UniqueIds in its response and the Core revision it planned against.
- Journal input: `MirrorDrift.ParseJournal` accepts the journal.read pipe reply (`{"status":"succeeded",...,"report":{journal_version 1}}`; any other status is refused), the report alone or the raw journal. Callers should send `peek: true` and `after_sequence` equal to `journal_after_sequence`; a reply with `peek: false` (it moved the add-in's baseline) is accepted with the note `journal_not_peek`. Sequences belong to one add-in session and journal_version 1 carries no session id: `journal_after_sequence` must come from the same Revit session, and a value beyond the reply's `current_sequence` is reported as `journal_session_mismatch` with no journal evidence used.
- Evidence completeness: `evidence.incomplete` with `notes` — `journal_incomplete` (`journal_complete` false, or a raw journal with dropped entries or recorder failures), `journal_has_more` (paged reply), `journal_session_mismatch`, `journal_after_mismatch` (the reply's `after_sequence` is later than `journal_after_sequence`, so entries in between are missing), `journal_detached` (the wrapper says `attached: false`: the recorder was not subscribed), `journal_not_peek`, `entry_truncated:<seq>` (an entry whose id lists were capped). Classifications in an incomplete report may be `unknown` where full evidence would not be.
- Unmapped: every snapshot `unmapped` entry is listed with classification `unmapped` (and the committed id it covers, if any) and never counts as drift, so a committed wall that became curved in Revit is reported as unmapped, not missing.
- Report: `drift_version` 1, canonical JSON (fixed key order; metres with 6 decimals, millimetre deltas with 3, degrees with 4, invariant culture; findings sorted by kind then UniqueId; unmapped by UniqueId; not_comparable by reason, kind, id and map key; out_of_scope by UniqueId), byte-identical across runs, cultures and input permutations. Diagnostic only, never persisted.
- Bounds: at most 20000 committed elements, 4096 journal entries and 2000 receipts (`drift_input_too_large`); `max_findings` (default 5000, at most 20000) caps findings, unmapped, not_comparable and out_of_scope lists, with true totals in `summary` and `truncated`.

## Localized validation of plan changes (P3-04)

`core/Bim.Core/LocalValidation.cs`, BCL only, no BIM-IR schema change. `LocalValidation.ValidateAll(project)` runs element rules on every element of a `Compiler.Validate`-clean project (`invalid_ir` otherwise): undecodable geometry of known kinds (GeometryCodec codes), hosted door/window/opening rules (`host_missing`, `host_ambiguous`, `hosted_geometry` — geometry must be `[offset, width]` metres along the host axis —, `host_extent`, `host_level`) and space/room boundary rules (`boundary_detached`: a bounding wall's axis box widened by half its thickness misses the space rectangle, 1e-6 m tolerance; `boundary_level`: the space and its bounding walls declare different levels). Findings are sorted by element id, code, message (ordinal); each names one element. `LocalValidation.Validate(before, after, plan)` refuses a plan that is not `Compiler.Diff(before, after)` (`plan_mismatch`) and evaluates the rules only on `Revalidated` = `plan.DirtyIds` present in after; the result also carries `Affected` (= `plan.DirtyIds`), `RevalidatedCount` and `TotalElements`. Invariant: a rule may read only the element and its Prerequisites closure in after (today two hops: prerequisites and their prerequisites), never its dependents (`Hosts`, `Bounded`, `OnLevel` or any Dependents traversal); any change in that closure makes the element a transitive dependent of a plan operation in after, so it is in `DirtyIds`. Levels compare as sets (all levels an element depends on); an element on no level is not compared. `Merge(previous, local)` expects `previous == ValidateAll(before)` (not checked) and keeps prior findings of elements outside `Affected`, adding the localized ones; `Agrees(before, after, plan)` checks `Merge(ValidateAll(before), Validate(...)) == ValidateAll(after)`. Evidence level: unit-tested (`tests/local-validation`: wall move/shorten with hosted openings, room boundary change, delete with dependents, no-op, level change, a level's kind changed to a non-level kind and back (findings two hops away), creates, element-order independence, 300 seeded single edits, 400 seeded rich steps of 1-3 edits (rehost, boundary rewiring, wall create/delete, upper level move/replace, level kind flips) with a per-step check that skipping any revalidated element whose findings changed disagrees with full validation, 50-room counter 6/551). `Validate` still runs `Compiler.Diff` once to check the plan, so the saving is in rule evaluation, not in structural validation.

## Affected-only documentation regeneration (P4-03)

`core/Bim.Core/DocRegeneration.cs`, BCL only, no BIM-IR schema or persisted format change. A caller-owned `DocumentationSet` names views (`floor_plan`/`ceiling_plan` of one BIM-IR level, `section` along one BIM-IR wall, `three_d` with a section box around BIM-IR walls), tags (one BIM-IR element in a plan view of the set), linear dimensions (two parallel BIM-IR walls in a plan view), schedules (every BIM-IR element of one kind, as a catalogue category), sheets and sheet placements (a view or schedule of the set on a sheet of the set) by stable ordinal keys (no surrounding white space, control character or `,`). The BIM-IR `plan`, `schedule` and `sheet` elements (RoomCompiler emits them) are not read unless a view, schedule or sheet names one in its optional `Bound`; the item is then unsupported (`element_missing`/`kind_mismatch`) while that element is missing or another kind. Malformed sets are refused with `ArgumentException` codes `doc_key_invalid`, `doc_key_duplicate`, `doc_text_invalid` (null required text or a lone surrogate in any name, number, title block, orientation, wall face, category, element kind or field), `doc_number_invalid`, `doc_view_kind_invalid`, `doc_view_elements_invalid`, `doc_view_unknown` (also a null view), `doc_view_not_plan`, `doc_sheet_unknown` (also a null sheet), `doc_dimension_references_invalid`; an invalid document reference is a `RevitCommandException` (`document_path_invalid`, `document_identity_invalid`).

`DocRegeneration.Full(project, set, bindings)` refuses a project `Compiler.Validate` rejects (`invalid_ir`) and turns each item into one P4-01/P4-02 catalogue command (`view.create_plan`, `view.create_section`, `view.create_3d`, `tag.create`, `dimension.create_linear`, `schedule.create`, `sheet.create`, `sheet.place_view`) computed from the project — plan level from `RevitBindings.Levels`; section line, depth and elevations from the level the wall resolves to (its first dependency that is a level with `[elevation]`, else 0); 3D box = wall axes ± half thickness; tag head = element plan centre + offset (wall axis midpoint, space centre, absolute opening midpoint, or for a hosted opening `[offset, width]` the point offset + width/2 along its only wall dependency; none is `host_missing`, several `host_ambiguous`); dimension line from the first wall's midpoint perpendicular onto the second — parsed by `RevitCommandProtocol.Parse`, or into one unsupported entry (`element_missing`, `kind_mismatch`, `geometry_invalid`, `host_missing`, `host_ambiguous`, `level_unbound`, `references_not_parallel`, `dependency_unsupported`, `command_invalid`). Every step and unsupported entry lists `Elements`, exactly the BIM-IR elements its result reads. Revit UniqueIds are inputs (`doc:<key>` or `element:<id>`, distinct placeholders in args); `Envelope(plan, step, uniqueIds)` fills them and re-parses (`input_field_unsupported` also for a null field, `input_unresolved` also for a null source, `input_invalid` also for a null UniqueId, `args_not_object`, or the catalogue's codes). Steps run views, schedules, sheets, tags, dimensions, placements, each by key; operation ids hash project, revision, after hash, key, schedule element kind, command, document, canonical args and sources.

`DocRegeneration.Affected(before, after, plan, set, bindings)` refuses a plan other than `Compiler.Diff(before, after)` (`plan_mismatch`; Diff's own `revision_conflict`/`invalid_ir` pass through), takes as candidates the items an element of whose reads (their `Elements`, in before or after) really changed (added, removed, or another kind, geometry or dependency list; provenance alone is not a change; not the transitive `DirtyIds` closure), computes each candidate in before and in after and regenerates only those whose content without operation id differs, plus the tags, dimensions and placements whose view, schedule or sheet is regenerated (their realized parent is new). Each step is byte-identical to that item's step in `Full(after)`. The caller retires the prior realization of every `Regenerated` key (no delete command is emitted). Every plan carries `InputDigest` (SHA-256 of the set by key and the bindings); `Affected` and `Agrees` assume the prior `Full(before)` used the same set and bindings, and `Merge(previous, update)` refuses another project (`project_mismatch`) or another digest (`input_mismatch`). `Merge` of `Full(before)` and the affected plan has the same content as `Full(after)` modulo operation ids (`SameContent`, `Agrees`). Evidence level: unit-tested (`tests/doc-regeneration`: per-kind command content, set validation and typed refusals, every unsupported path, exact regenerated sets for wall move/rotation, host wall move under a hosted window, level change (bound and unbound) and kind change, door delete/create/dependency reorder/sill and height, wall thickness and height, wall dependency reorder that keeps its level, ambiguous host, space change, provenance-only edits, bound BIM-IR sheet/schedule/plan changes, no-op, deleted dimensioned wall; element-order independence; soundness (any item whose full result changed is regenerated) and a strict minimality oracle (a regenerated item without a regenerated parent has a different full result in `Full(before)` and `Full(after)`) on every case and on 300 seeded chained edits; 50-room counter 2/404). Remaining over-approximation, by design: tags, dimensions and placements re-run with a regenerated parent even when their own command is unchanged. A schedule refreshes only when its membership (its `Elements`) changes, since Revit schedules show element values live. Not verified-in-revit.

## Circulation model for layouts (P7-04)

`core/Bim.Generative/Circulation*.cs`, BCL only, no BIM-IR schema change and no change to `AlternativeRanker`, `AlternativeSetSerializer` or any existing canonical output. `CirculationAnalyzer.Analyze(brief, plan, options)` turns a feasible `SpacePlan` into a `CirculationModel`.

- Doors are candidates, not a door design: every shared wall of two same-level rooms at least the door width long (default the plan's, 1e-7 m tolerance) gets one door of that width centred on the shared part of the wall. "Reachable" therefore means connected in the room adjacency graph through such walls; `used` marks the doors some route crosses. Doors are ordered by level, then `from`, then `to` (instance ids, ordinal, `from < to`) and named `door:<from>/<to>`.
- Entrance: one door centred on a side of a level-0 room lying on an allowed street edge (`EntranceEdges`, default south, east, north, west in that order, because the brief records no street). Lot = brief site, else plan footprint. Candidates: `EntranceRoomId` when given; otherwise level-0 non-bedroom rooms whose id or name matches an `EntrancePatterns` glob (`hall*`, `*entrance*`, `*entry*`, `*foyer*`, `*lobby*`, `*vestibul*`, `*palier*`), then the remaining level-0 rooms that are neither bedrooms nor wet rooms; each group largest first, ties by instance id. The entrance door goes from `@exterior` to the entrance room.
- Room classes (globs on room id or name, case-insensitive): bedrooms `BedroomPatterns` (`*bedroom*`, `*dormitorio*`); wet rooms `PassThroughPatterns` (`*bath*`, `*baño*`, `*bano*`, `*toilet*`, `wc*`, `*ensuite*`, `*en-suite*`, `*vestidor*`, `*closet*`, `*dressing*`); every other room is dry.
- Routes: deterministic shortest paths over door midpoints (straight lines inside rectangular rooms, ending at the room centre), bedroom-free when possible; equal lengths keep the earlier door in door order. Hard checks: `circulation_entrance`; per level-0 room `circulation_reachable`, plus `circulation_bedroom_access` (bedroom) or `circulation_passage` (dry room) requiring a route that does not pass through a bedroom. Only wet rooms may sit behind a bedroom. Rooms off level 0 get the soft `circulation_unsupported` outcome (no stairs are modelled); they never make a plan invalid.
- Refusals: `circulation_plan_invalid` (infeasible or empty plan, bad rectangle, duplicate instance id, overlapping rooms naming the pair `a/b`, no lot) and `circulation_options_invalid`. Routes sort by instance id, so the model ignores room order; `CirculationSerializer` writes canonical `circulation_version` 1 JSON (diagnostic, not persisted).

`CirculationRanker.Rank(brief, plans, CirculationScoring)` / `Generate(brief, AlternativeOptions, CirculationScoring)` is an opt-in composition over `AlternativeRanker`. It keeps the six base criteria (raw, normalized and detail unchanged), re-weights them over the sum of the seven given weights and appends `circulation` (default weight 0.15) over the level-0 rooms: raw = mean route length in metres, each room without a valid route counted at the penalty P = sum of (width + depth) of the level-0 rooms (an upper bound on any shortest route); normalized = valid/rooms * L/(L + raw), L = sqrt(level-0 room area). Losing a valid route therefore never raises the score for the same geometry. The criterion detail records the circulation weight (given and effective) and `RequireValid`, and for a refused model or a missing entrance it names the failed codes. With `RequireValid` (default) an alternative whose circulation fails a hard check is infeasible, with those checks as reasons. Weight 0 without the gate reproduces the base totals and ranks bit for bit. Evidence: unit-tested (`tests/generative/CirculationTests.cs`: exact route lengths on crafted plans, a symmetric tie, a shorter route with more doors, partial walls and 1e-8 m tolerances, wet versus dry rooms behind a bedroom, overlap refusal, entrance street edges and fallback, an independent breadth-first and Floyd-Warshall oracle over apartment-2br seeds, ranked 1/2/3-bedroom prototypes and a two-level brief through `Generate`, the gate, lenient monotonicity, weights and provenance, determinism across runs, room orders and cultures). Gaps: no corridors are carved, no door swing or clearance, single entrance, no stairs (upper levels unanalysed), and prototypes do not apply the gate yet.

## Release packaging manifest (P10-04)

Evidence: unit-tested (`tests/packaging/test-package.ps1`, run by `scripts/verify.ps1` on the ubuntu and Windows core jobs: two clean builds compared byte for byte, layout, exact `<version>+<commit>` stamp and git fallback, forbidden-content scan, packaged CLI starts, tamper/missing/extra/forbidden/duplicate/field/VERSION/symlink detection, refused existing output, failure-path cleanup via fake `dotnet` (failing, and leaking `RevitAPI.dll`), hostile temp parent with injected MSBuild files leaves the package byte-identical). ## query.journal catalogue query (P2-05)

`query.journal` (`core/Bim.Core/RevitCommandsJournal.cs`, executor `runtimes/revit-native/CommandsExecutorJournal.cs`) is the read-only catalogue form of the raw pipe Operation `journal.read` (P2-03). It sits in the mirror catalogue part after `query.snapshot`, so it is listed as MCP tool `revit_query_journal` (`readOnlyHint` true, `_meta` permission level `read`) and the P10-03 policy classifies it `read` on copies and real projects.

- Args (all optional, `{}` = journal.read defaults): `peek` boolean (keep the baseline), `after_sequence` integer >= 0 (default: the last read's baseline), `max_entries` integer 1..256 (default 256). Anything else, a wrong type, a negative or non-integer sequence or a cap outside 1..256 is `args_invalid` at `args.<member>` before the pipe. The bound `JournalQueryArgs.Options` equal `MirrorJournalReadOptions.Parse` of the same JSON. An `after_sequence` past the journal's last sequence is `args_invalid` at `args.after_sequence` from the executor (the raw journal.read answers `{"status":"failed","code":"journal_after_sequence_invalid"}` there, since App.Execute serialises the exception message as the code).
- Reply: a query success whose readback is `{"attached","dropped","skipped_add_in","failures","unidentified","report":{journal_version 1}}`, byte-identical to the journal.read reply after its `status` and `verification` members (`RevitJournalQuery.Body` serializes both). Same tracker and baselines as journal.read: a read without `peek` consumes the in-memory baseline shared with journal.read and every other client, so the tool description says so first and recommends `peek: true` unless the caller owns the baseline. No transaction, no receipt, nothing written to the document. A hand-written golden of the journal.read bytes, in the member order of `tests/mirror-journal/fixtures/drift/journal-read-reply.json`, pins both replies.
- Drift input: `MirrorDrift.ParseJournal` refuses the bare readback (`drift_journal_invalid`: no status, no top-level entries); `RevitJournalQuery.AsJournalReadReply(readback)` restores the journal.read reply bytes, which ParseJournal reads with attached/dropped/failures completeness. A string that is not a readback object is refused `journal_readback_invalid`.

## Element QA recipe pack (P5-05)

`skills/bim.qa.element-basics` (qa 1.1.0, priority 50, 23 rules, 13 parameters) and `core/Bim.Core/SkillElementValidator.cs` evaluate element-targeted skill rules over BIM-IR walls, doors and windows with no schema change. Rules name a quantity with an explicit unit suffix (`_mm` or `_m`; `host_level_mismatch` is a count); millimetres are metres x 1000 rounded to 6 decimals. A `ratio_min` whose two properties have different units is `unit_mismatch`, never divided.

- Walls `[ax,ay,bx,by,height,thickness]`: `length`, `thickness`, `height`.
- Openings, host = the single dependency that is a wall. Two layouts are read:
  - axis layout `[ax,ay,bx,by,sill,height]` (IntentCompiler, MirrorMapper): `width` (distance between the ends), `height`, `sill`, `start_clearance`, `end_clearance` (projections on the host axis), `head_clearance` (host height - sill - height), `axis_offset` (largest perpendicular distance from the axis line);
  - hosted layout `[offset, width]` (accepted by LocalValidation and DocRegeneration): `width`, `start_clearance` = offset, `end_clearance` = axis length - offset - width, `axis_offset` = 0; `sill`, `height` and `head_clearance` are `hosted_layout`.
  - `host_level_mismatch`: 0 when the opening's first level dependency equals its host wall's, else 1; `level_missing` when either has none.
- Semantics: clearances are measured along the host wall **axis span**, not the clear span (axis minus half the joined walls) that IntentCompiler enforces, so the pack is looser than the compiler at joined corners. "Inside host" is min `opening_clearance_min_mm` (default -0.001 mm, matching IntentCompiler 1e-6 m and MirrorMapper 1e-3 mm) on start/end/head clearance and sill, plus max `opening_axis_tolerance_mm` (1 mm) on `axis_offset`; an opening flush with a wall end measures exactly 0. Doors also need `sill_mm <= door_sill_max_mm` (0.001 mm; BIM-IR doors sit on their level) and every opening `host_level_mismatch <= 0`.

Each `ElementFinding` carries element id and kind, qualified rule id, skill id and version, local rule id, op, property, unit, measured, bound and bound source (`<skill>:parameter:<name>`, `<skill>:rule:<id>` or `override:<skill>/<name>`), host id, severity and detail. Missing data is `NotEvaluable` with a typed `ElementReasons` code (`property_unknown`, `threshold_not_number`, `unit_mismatch`, `geometry_invalid`, `shape_unsupported`, `hosted_layout`, `host_missing`, `host_orphan`, `host_ambiguous`, `host_geometry_invalid`, `host_shape_unsupported`, `host_degenerate`, `level_missing`, `ratio_undefined`), never a pass; `Compliant` requires every finding to pass. BIM-IR walls are straight six-value axis segments, so curved walls are `shape_unsupported` (no arc length). Findings are ordered by element id then qualified rule id; element rules that matched no element are listed in `UnusedRuleIds`; duplicate element ids are refused, duplicate rule ids are refused by the manifest parser at load; run-time overrides must lie in the declared range and must not invert a `*_min*`/`*_max*` parameter pair. The `bim.qa.room-basics` element rules are now evaluated too (`room_bounding` and `operation` are not BIM-IR quantities and report `property_unknown`). Unit-tested in `tests/skills/ElementSkillTests.cs`; not run against Revit.

## Multi-command batch with one undo (P1-07)

`command.batch` (`core/Bim.Core/RevitCommandsBatch.cs`, executor `runtimes/revit-native/CommandsExecutorBatch.cs`) is the last catalogue entry (MCP tool `revit_command_batch`, write-copies, `destructiveHint: true` because a step may change or delete elements, `idempotentHint: true`). Same envelope (protocol_version 1), schema subset, copies-only and link guards and receipt store as every write; earlier commands are unchanged.

- Args: `{steps: [{operation_id, command, args}]}`, 1 to 50 steps. `command` is an enum of `RevitCommandCatalogue.BatchStepCommands`: every catalogue write except `command.batch` itself and `document.save` (a save cannot run inside a transaction group); queries and `view.export_image` are refused. Each step's `args` is validated with that command's own schema and typed binder; every refusal path is rewritten under the step (`args_invalid` at `args.steps[1].args.height_mm`, `length_invalid` at `args.steps[2].args.curve.start[0]`, `args.steps[0].command`, ...). Any step whose args carry `dry_run: true`, whatever its command, is refused (`args_invalid` at `args.steps[i].args.dry_run`). Unreadable text in a step (a lone surrogate escape) is `envelope_invalid` at `args.steps[i]`. Step `operation_id`s use the envelope pattern, are distinct (ordinal) and differ from the batch `operation_id` (`args_invalid` at `args.steps[i].operation_id`, checked by `RevitCommandProtocol.Parse`). The whole batch, step order included, is one canonical request: its hash is the batch replay key. The client checks the family.load source guard for every family.load step (`family_source_refused` at `args.steps[i].args.path`); the add-in repeats it per step.
- Executor: admission (identity, copies-only, link, read-only/family/workshared/open-transaction) once for the batch document. The step loop is Autodesk-free (`RevitCommandBatch.Run`, unit-tested with a fake runner); the executor supplies only the TransactionGroup calls, `Dispatch` per step, `Document.GetElement(uid)` and the receipt persist. Before any step runs: a step `operation_id` already in the receipt store is `operation_id_conflict` at `args.steps[i].operation_id` (a step never replays inside a new batch), and stored receipts + steps + 1 above `MaxReceipts` (2000) is `transaction_failed` (receipt store full). One outer `TransactionGroup`; each step is its stand-alone envelope (`RevitCommandBatch.StepEnvelope`, hash = SHA-256 of its canonical text) run through the ordinary write path (its own nested group, transaction, failure processing, readback before and after commit, step receipt), assimilated into the outer group. The first step that throws, fails or replies with a receipt that does not answer it rolls the outer group back exactly once (every earlier step and its receipt undone; no later step runs) and the reply is that step's code with its field moved under the step (`args...`, `operation_id`, `command` or none become `args.steps[i]...`; batch-level fields such as `document.path` are kept) and detail `step i (<command>, operation_id <id>) failed: <detail>; the whole batch was rolled back and nothing was written`. After the last step every net created or modified UniqueId must still exist (else `transaction_failed` at `args.steps[i]` naming the step that created or modified it, rolled back); then the batch receipt is stored beside the step receipts (a persist that throws rolls back too) and the outer group is assimilated: one undo entry named `BIM Agentic OS command.batch <operation_id>`. Re-sending the same batch `operation_id` and request replays the stored reply (`replayed: true`) without writing; a different request under it is `operation_id_conflict`.
- Reply: `created`/`modified`/`deleted` are the net change in step order (UniqueIds compared case-insensitively; created then deleted is in none, created then modified only in `created`); warnings are prefixed `step <i> <command>: `; readback `{batch: {steps, undo_entries: 1}, steps: [{index, operation_id, command, response}]}` where `response` is each step's own reply with its readback and receipt; those nested receipts stay `replayed: false` even when the whole batch is replayed (only the top-level receipt says `replayed: true`).
- Limits: the whole envelope must fit the 65536-character wire line (fifty plain walls do). The batch receipt repeats the step replies: a 50-step batch of family.load-sized (about 4 KB readback) replies stores about 0.5-0.7 MB (step receipts and the batch receipt about equal; asserted under 0.8 MB, batch receipt under 0.4 MB), so the 4 MB store holds about six such batches; a store over 4 MB refuses the write and rolls back. An `element.delete` step must confirm the dependents a dry run reported before the batch; earlier steps that add elements hosted by the target (doors in a wall the batch then deletes) change the dependents, so the delete step is refused and the whole batch rolled back. The step `args` member has no `"type":"object"` in the batch schema because the schema subset only allows closed objects; the step's own schema checks it.
- Evidence: unit-tested contract and Autodesk-free decisions (`tests/revit-commands/CatalogueBatch.cs`, `tests/mcp`, `tests/audit`); the executor is compiled against the Revit 2025 reference assemblies only. Unverified in Revit: nested-group behaviour of StairsEditScope/SketchEditScope steps and the single undo-list entry.

- Evidence: unit-tested (`tests/generative/FacadeTests.cs`: exact windows on crafted plans, side ties, two windows on two short sides, minimum-width bump, ventilation governing, sill/head options, an upper level, interior, too-short and party-wall rooms, a courtyard void, wet rooms skipped, applies_if held/exceeded/unknown, parameter thresholds and overrides, bounded sizing at the extreme options, refusals, a SkillRoomValidator cross-check, an independent side-sampling oracle with a point-sampled 2.5 cm raster flood fill for voids, reading thresholds from the pack JSON over ranked 1/2/3-bedroom prototypes with per-alternative typed outcomes, determinism across runs, room orders and cultures). ## P2-06 Element provenance ledger

`core/Bim.Core/Provenance.cs` and `ProvenanceLedger.cs`, BCL only; a new standalone format, no BIM-IR schema change (the existing `Element.Provenance` record is untouched). `ProvenanceLedger` is an append-only, in-memory ledger of where each BIM-IR element id came from, with `Serialize()` / `ProvenanceLedger.Load(json)`.

- Sources (closed set, `ProvenanceKinds`): `intent` (`intent_id`, `rule_id`: plain text, 1-256 chars, no padding), `catalogue_command` (`command`: dotted lower-case name up to 128 chars, and on `Append` also present in today's `RevitCommandCatalogue`; `Load` checks the syntax only, so stored records of a command later removed still load; `operation_id` matching the envelope pattern), `external_edit` (`document_unique_id`, `journal_sequence` >= 1, `recorded_at` `yyyy-MM-ddTHH:mm:ss.fffZ`, `unique_id`, `change` `added`/`modified`; ids lower-case; the element id must equal `MirrorSnapshotMapper.Id(document, unique_id)`), `cad_import` (`file_sha256` 64 lower-case hex, `entity_handle` 1-16 upper-case hex). `ProvenanceSource.FromJournal(MirrorJournalEntry)` turns one external journal entry into one source per added and modified UniqueId (add-in entries and deletions give none); when the entry's added or modified list was capped it returns `provenance_journal_truncated` with the ids still listed (the caller must resynchronise the rest, e.g. from a snapshot diff). `ProvenanceSource.Create(kind, fields)` builds a source from strings; an unknown kind is `provenance_kind_unknown`.
- `Append(elementId, source)`: `appended` (seq n+1, `prev_hash` = previous hash, `hash` = SHA-256 of the entry without hash), `replayed` (same replay key and content: the stored entry, nothing appended), `provenance_conflict` (same key, other content), `provenance_record_invalid` with the offending member as detail. Replay key = element id + kind + `intent_id` (the `rule_id` is content, not key: one intent originates an element through one rule, so the same intent and element under another rule is `provenance_conflict`; a recompiled intent that changes rules needs a new intent id) | `operation_id` | `document_unique_id` + `journal_sequence` + `recorded_at` (the journal sequence restarts with the add-in) | `file_sha256` + `entity_handle`. No edit, delete, insert or clear member exists; `Entries`, `ByElement` and `BySource` return copies. Caps (`ProvenanceLimits`, default 100000 entries and 64 MiB of JSON text): `Append` past either is `provenance_too_large` (a replay is still answered), `Load` refuses longer input before parsing and the first entry past the entry cap with `provenance_too_large`.
- Queries: `ByElement(id)` (append order, origin first), `BySource(kind, sourceId?)` matching `intent_id`, `operation_id`, `document_unique_id` or `file_sha256` (unknown kind refused).
- Format: `{"provenance_ledger_version":1,"entries":[{"seq","element_id","source":{"kind",...fields},"prev_hash","hash"}]}`, compact Utf8JsonWriter output with its default escaping, byte-stable and culture independent. Load refuses with the 1-based entry number: `provenance_json_invalid`, `provenance_version_unsupported`, `provenance_kind_unknown`, `provenance_record_invalid`, `provenance_sequence_broken`, `provenance_chain_broken`, `provenance_hash_mismatch`, `provenance_duplicate_entry`, `provenance_conflict`, and `provenance_not_canonical` for any text not byte-identical to the re-serialization. `Load` never throws on bad input: unpaired surrogates in the text are `provenance_json_invalid@json_text`, escaped lone surrogates are `provenance_record_invalid` at the member (`@source`/`@entry` for a member name, `provenance_json_invalid@member` at the top level); details are fixed tokens or member names, never parser messages. `ProvenanceLedgerFormat.Write`/`ComputeHash` throw `ArgumentNullException`/`ArgumentException` for null arguments, entries, sources or hash text.
- Limits: the chain is unkeyed (a full rewrite with recomputed hashes, or dropping trailing entries, is a valid ledger; keep `HeadHash`/`Count` outside the file to detect that); not wired into the CLI, MCP, the intent compiler or the CAD importer yet, and no file persistence/locking. Evidence: unit-tested (`tests/provenance`, gate `provenance-tests`: golden bytes with an independently computed hash chain, all four kinds, journal mapping, queries, replay and conflicts, malformed records, round trip and culture independence, tamper/reorder/duplicate/non-canonical refusals, append-only surface).

## P10-06 jurisdiction rule-pack registry

`core/Bim.Core/Jurisdiction.cs`, `JurisdictionRegistry.cs`, `JurisdictionValidator.cs`, BCL only; no BIM-IR schema, skill manifest or existing persisted-format change.
- A code pack declares its jurisdiction in a sidecar `skills/<id>/jurisdiction.json` (new standalone format, `jurisdiction_version` 1; `SkillLoader` ignores it): `code` (`<two-letter country>.<locality>`, e.g. `ar.caba`), `pack` (the directory's skill id, which starts with `code.`), optional `country_names` / `municipality_names` aliases, `stub` and optional `note`. Strict parse with typed codes (`json_invalid`, `member_unknown`, `member_duplicate`, `member_missing`, `type_invalid`, `value_invalid`, `version_unsupported`, `code_invalid`, `pack_mismatch`, `entry_duplicate`, `too_many_items`, `input_too_large`); loading never follows links and re-checks the skill directory and file after the read and the skills-root boundary (`path_unsafe`), refuses empty or special files and a directory named jurisdiction.json (`not_regular_file`), I/O failures are `read_failed`, and a skills root `SkillLoader` refuses is `skills_invalid`.
- `JurisdictionRegistry(catalog, claims)` validates hand-built claims like sidecars (dropped with `code_invalid`, `pack_mismatch` or `value_invalid` for missing or malformed name lists and lone surrogates), drops claims on missing (`pack_missing`) or non-code (`pack_not_code`) packs, reports a code claimed twice (`claim_duplicate`) and two jurisdictions whose country and municipality aliases coincide after accent/case folding (`alias_overlap`; both stay registered, metadata selection between them is ambiguous) and lists code packs without a claim. Claims sort by code then pack, issues by code/subject/detail (ordinal).
- `Select(ProjectJurisdiction(Code, Country, Municipality))` (a caller record, not BIM-IR): a code (trimmed, lower-cased) needs exactly one claim, and metadata given with it must agree (`jurisdiction_conflict`); without a code both country and municipality are required (`jurisdiction_incomplete`) and are matched, accent/case/whitespace-insensitively, against the code labels and aliases. A stub claim is selected only with `allowStub: true`, else `jurisdiction_stub_refused`. Refusals: `jurisdiction_unspecified`, `jurisdiction_invalid` (also any lone surrogate in the input), `jurisdiction_unknown`, `jurisdiction_ambiguous` (duplicate claim, or metadata matching more than one jurisdiction).
- `JurisdictionValidator.Validate(registry, project, rooms, parameters?)` resolves the selected pack with its requirements and runs the unchanged P5-02 `SkillRoomValidator`; the `JurisdictionValidation` envelope adds the jurisdiction, `matched_by`, and per resolved pack its id, version, kind, stub flag and a source_confidence summary (rule counts per cited / owner-confirmed / to-verify and the lowest level). Each resolved pack reports the registry claim on it, so a required pack that is itself a (stub) code pack carries its own jurisdiction and stub flag; a required stub pack also needs `allowStub`. `rooms.stub_rules` marks findings that come from a stub pack. Refusals: the selection refusal, `jurisdiction_stub_refused`, `pack_unresolved`, `input_invalid` (duplicate room ids, rejected parameter overrides, room ids, names or override keys with a lone surrogate). `ToJson()` is deterministic (`envelope_version` 1).
- Packs: `skills/ar.caba.codigo-edificacion` (real, per-rule confidence) and `skills/xx.example.codigo-ejemplo`, a fictitious STUB/example jurisdiction (`xx` is no country) whose invented rules are all to-verify; it exists only to prove multi-jurisdiction selection and is not law.
- Evidence: unit-tested (`tests/skills/JurisdictionTests.cs`, gate `skills-tests`).

## P5-04 style skill defaults feed the intent compiler

`core/Bim.Core/IntentSkillDefaults*.cs`, BCL only; no change to the layout intent format, its JSON or BIM-IR. `IntentDraft` is a new in-memory input mirroring `LayoutIntent` with the defaultable fields optional (`IntentDraftLevel.ElevationMetres` + `Storey`, `IntentDraftWallType.Name/ThicknessMetres/HeightMetres` + `Role` exterior|interior, `IntentDraftOpening.SillMetres/HeightMetres`). `IntentSkillDefaults.Fill(draft, SkillResolution)` fills open fields from the resolved P5-03 settings before compile; `IntentSkillDefaults.Compile(projectId, revision, draft, resolution)` is Fill followed by the unchanged `IntentCompiler.Compile`.
- Fill rules (field <- default key): `levels[k].elevation_m` <- `level-elevation-ground` (storey 0, no default), `level-elevation-from-storey` (storey x `level.height_m`) or `level-elevation-above-explicit` (highest explicit lower-storey level's elevation + storey difference x `level.height_m`); `wall_types[k].name` <- `wall.<role>.type`; `wall_types[k].thickness_m` <- `wall.<role>.thickness_m`; `wall_types[k].height_m` <- `level.height_m`; window `sill_m` <- `window.sill_height_m`, door `sill_m` <- rule `door-sill-on-level` (0); window `height_m` <- `window.head_height_m` minus the effective sill (derived), door `height_m` <- `door.height_m`.
- Provenance: `IntentFieldSource` per defaultable field (sorted by field path): value text, origin explicit|default|derived|rule, rule id and the `SkillTrace`s of the defaults read. Explicit draft values always win, are reported `explicit`/`explicit` with no trace, and are validated only by the compiler.
- Levels: an open elevation requires `Storey` (`default_missing` otherwise, never a silent 0 m); storeys are >= 0 (`storey_invalid`; below-ground levels take an explicit elevation and no storey) and unique (`storey_duplicate` on the smaller key); an explicit level's storey is kept and anchors open storeys above it; elevations of all levels with a storey must rise strictly with storey (`storey_order_invalid`).
- Windows: an explicit height with an open sill takes the style sill; style sill + height above `window.head_height_m` is `derived_value_invalid` on `sill_m`. `room.min_clear_height_m` fills no field and only takes part in the consistency checks. Default validation is deliberately strict: an invalid recognised default refuses even a fully explicit draft.
- Draft keys must be unique per levels, wall_types and openings (`draft_key_duplicate` on `collection[key]`, checked first).
- Refusals (`IntentIssue`, sorted; `Compile` throws `IntentException` with the first code and its key as Field): `defaults_resolution_failed` (key "", Field null); `default_type_invalid` / `default_value_invalid` for any present recognised default (non-positive thickness, level, clear or head height, negative sill, blank type name); `default_inconsistent` (sill >= head, clear height > level height, head > clear height); `default_missing` naming the open field and the absent key (never a silent 0); `derived_value_invalid` (explicit sill at or above the default head).
- Determinism: derived numbers rounded to 1e-9 m, invariant culture; one draft under `bim.style.compact-modern` and `bim.style.warm-masonry` compiles to two different projects, each byte-stable on repeat and independent of draft list order.
- Evidence: unit-tested (`tests/intent/SkillDefaultsTests.cs`, run from `tests/intent/Program.cs`, gate `intent-tests`).
